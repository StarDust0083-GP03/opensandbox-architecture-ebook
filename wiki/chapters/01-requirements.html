需求篇：Agent 执行环境要满足什么

先把需求摊开。不然后面看到「为什么 Docker 只映射一个端口」「为什么暂停要提交镜像」「为什么出向策略默认拒绝」，会觉得是风格问题；其实每一条都在回答这里列出的某个约束。

一个教学场景

假设团队在做一个修 bug 的编码 Agent。它的典型工作循环是：

  1. 读一个仓库；
  2. 跑测试，看哪条失败；
  3. 改代码；
  4. 再跑测试；
  5. 把 diff 交回给人类审。

这个循环里有四种东西要被真实执行：shell 命令、文件读写、语言运行时（真正跑测试）、以及对外的网络访问（装依赖、查文档）。同时它有三个隐含要求：并行（一个团队同时跑几十个任务）、可清理（跑完就该消失）、不可信（模型写的代码可能 rm -rf /，也可能拿沙箱当跳板去打内网）。

这就是本书所有讨论的出发点。下面把需求拆成六条，每条都对应上游的一个具体机制。

需求一：隔离必须是运行时的性质，不是约定

「别删错目录」靠代码审查解决，「不能删到别人」只能靠隔离。容器名空间能挡住大部分误操作，但挡不住内核漏洞导致的逃逸。所以需求要写成可替换的层次：

  • 默认：标准容器（runc）。
  • 加强：用户态内核（gVisor）或轻量虚拟机（Kata，含 QEMU 与 Firecracker 两种）。
  • 极致：每个沙箱一台 microVM。

上游把这件事做成了服务端配置（[secure_runtime]，type 取 ""/gvisor/kata/firecracker），调用方不改代码。教学推演的理由很直接：隔离级别是运维对整台机器的承诺，不该让每个调用方各自决定，否则同一个集群里会混着不同强度的边界，审计时说不清。

需求二：创建要快，且快在「已经存在的容量」上

Agent 的交互是对话式的。用户等 30 秒才看到一个空沙箱，体验上等于失败。但「快」有两种做法，代价完全不同：

  • 把创建流程优化到极致：省掉不必要的 API 调用、并行拉镜像。
  • 让创建不创建：提前准备好容量，创建只是把容量认领出去。

上游两条都做了。Kubernetes 侧是 Pool：预热 Pod 池，分配是把 Pod 标注给某个 BatchSandbox，不再经过调度器。Fast Sandbox 侧更激进：模板预构建成 golden image，创建时恢复一份 vmstate 快照，而不是启动内核。

文档给的数字可以建立量级感：同一份 Performance 页里，Kubernetes 后端启用 Pool 后交付 100 个沙箱总耗时 0.92 秒；Fast Sandbox 在 ACK 两节点集群上的 SDK 创建 p50 是 64.0 ms（串行 100 次，预热后）。这两个数字的测量边界完全不同，不能互相替代，后面第 8 篇会专门讲怎么读它们。

需求三：沙箱里要有一套「能干活」的接口

隔离环境本身是个空壳。Agent 需要的是：执行命令并实时看到输出、后台跑长任务、上传下载文件、开一个交互终端、跑 Jupyter 内核、看 CPU/内存。这些不能靠「SSH 进去」解决，因为 SSH 是给人用的协议，没有结构化输出，也没法做细粒度权限。

所以需求是三件事：

  1. 一个数据面 API，覆盖命令、文件、PTY、代码执行、指标；
  2. 流式语义，输出要边跑边到，不能等命令结束；
  3. 明确的终止语义，让客户端能区分「跑完了」「失败了」「连接断了」。

第三条最容易被忽略。上游为此规定了 execution_complete 事件携带 exit_code，并且明确写了「流在终止事件之前结束，不能推出成功」。第 9 篇会拆这段。

需求四：沙箱要能被访问，但访问路径不能由调用方猜

沙箱里跑的服务（8080 的 web 应用、5900 的 VNC、8888 的 Jupyter）需要被外部访问。三种拓扑三种答案：单机 Docker 是宿主端口映射，Kubernetes 是 ingress 网关，两者都不通时是控制面反向代理。

如果让调用方自己拼地址，就出现两个问题：不同后端要写不同客户端代码；拓扑一变，所有调用方同时坏掉。所以上游把「怎么访问」也纳入契约：GET /sandboxes/{id}/endpoints/{port} 返回一个已经可用的地址加上必须携带的请求头。客户端不需要知道后面是 Docker 还是 Istio 还是自建网关。

这条需求的隐含代价：endpoint 解析必须便宜，因为它会被反复调用；而且它不能证明沙箱存在（Fast Sandbox 的路由是本地签名，不解引用就不查后端）。第 10 篇会讲这个「签发与就绪解耦」的选择。

需求五：出向流量默认拒绝，并且可解释

沙箱里的代码会访问外部世界：装 pip 包、调模型 API、拉 git 仓库。默认放开等于把生产网络的出口交给一段模型生成的代码。

需求因此变成三层：

  • 能按域名控制，因为运维想说的是「只允许 pypi 和 github」，不是「只允许 10.2.0.0/16」；
  • 能落到包级，因为只做 DNS 过滤时，一个已经解析出的 IP 可以绕过域名规则；
  • 平台能压过用户，因为租户策略不该能打开平台明令禁止的目标。

上游的实现是两条层：DNS 过滤 + nftables 默认拒绝，外加平台覆盖规则（deny.always / allow.always）与端口底线。第 11 篇拆。

还有衍生需求：Agent 需要调第三方 API，但密钥不能进沙箱。这变成了 Credential Vault（第 12 篇）：出向请求在沙箱外的代理里被加上凭据，沙箱进程只看到「已经认证好的流量」。

需求六：生命周期要比「创建/删除」更细

Agent 任务有长有短。短任务跑完就该消失；长任务在等人类回复时不该持续占 CPU；被中断的任务希望保留现场，下次接着跑。

于是需要四件事：

  1. 绝对过期，而不是空闲超时——否则重启会把 TTL 重置，寿命无法审计；
  2. 暂停/恢复，且恢复后沙箱 ID 不变；
  3. 快照，从运行中的沙箱做出可复用的起点；
  4. 访问即续期，让活跃会话不被 TTL 掐断。

上游同时提供「暂停」和「快照」两个概念，看起来重复，实际边界不同：暂停是内部机制，目的是释放算力、保留连续性；快照是公开产物，目的是把状态变成可复制的制品。第 13 篇会把这两个词分开。

非需求：明确不做的

需求文档的价值一半在「不做什么」。从 ROADMAP 与文档能读出几条克制的边界：

  • 不在生命周期 API 上做稳定的 v1 承诺。ROADMAP 的「Not Currently Planned」第一条就是不宣布稳定 v1，理由是对语义、运行时行为与 SDK 兼容性还不够成熟。
  • 不假装控制面已经水平扩展。默认部署是单活；PostgreSQL 只支撑一个很窄的多副本能力（快照创建协调），文档原话是「General load-balanced lifecycle HA is not supported yet — and is not pretended」。
  • 不把所有后端做成功能等价。模板只支持 Fast Sandbox；生命周期钩子只支持 Kubernetes 容器后端；Fast Sandbox 拒绝卷挂载与 credentialProxy。这些差异写进了 docs/api/implementation-compatibility.md，而不是用「即将支持」掩盖。
  • 不承诺沙箱文件系统持久。暂停/快照之外，容器可写层随 Pod 消失；文档明确说进程退出、OOM、驱逐、节点丢失都不会自动快照。

六条需求的相互关系

这六条不是并列的清单，它们互相拉扯：

  • 要快（需求二）就要预热容量，预热就与「每个请求定制环境」（需求四、六）冲突。上游的解法是把定制性从 Pod 挪到 task 与注解上。
  • 要强隔离（需求一）就要 microVM，microVM 与「每沙箱一个 sidecar」（需求五）冲突。上游的解法是每个 Fastlet Pod 一个共享 egress 进程，按 subject 分治。
  • 要可解释的出向策略（需求五）就要 L7 拦截，拦截就要在沙箱里装 CA，这又削弱了「沙箱不信任自己环境」的假设。上游的选择是默认关、开启时把 CA 装进系统信任库，并把配置面标为实验。

第 18 篇会把这些冲突集中算一遍账。现在只需要记住：后面每一个看起来奇怪的设计，都是某两条需求打架后的落点。

本章要点

  • 六条需求：运行时级隔离、快速创建、可干活的数据面、契约化的访问路径、默认拒绝的出向控制、细粒度生命周期。
  • 每条需求在上游都有一个可指认的机制，也都有一个明确的「不做」。
  • 需求之间是冲突关系，不是叠加关系；冲突点集中在第 6、8、11、18 篇。
