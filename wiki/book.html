前言：沙箱为什么是 Agent 的地基

模型生成的代码要被真的执行，才叫 Agent。执行就要有地方放进程、放文件、放网络出口，还要保证这段代码弄不坏别人的东西。这三件事在传统后端里由「部署」解决，在 Agent 场景里必须由「一次请求」解决：用户说一句话，几秒之内要有一个隔离环境可供读写、联网、跑测试，用完就消失。

OpenSandbox 就是为这件事写的。它的自我描述很克制：给 AI 应用提供隔离环境来执行代码、运行命令、管理文件、操作浏览器或桌面；本地用 Docker 起步，在 Kubernetes 上扩到集群，对外保持同一套沙箱 API。

这本书要回答的问题只有一个：当客户端发出 POST /v1/sandboxes 之后，中间到底发生了什么，为什么会这样设计。

这本书怎么来的

写作基于 opensandbox-group/OpenSandbox 仓库在提交 c2f55b20e945d89efe3d35220942a997a3551751（2026-10-30）的快照。方法是静态阅读：源码、specs/ 下的 OpenAPI 契约、docs/ 下的架构与运维文档、oseps/ 下的设计提案，以及 README、CHARTER、ROADMAP。

本书没有做的事，提前说清楚：

  • 没有部署这套系统，没有跑它的端到端测试，也没有做性能、安全或兼容性验证。文中出现的数字全部来自上游文档，并标明出处与适用条件。
  • 没有把上游文档翻译成中文再贴一遍。每个章节都按「问题 → 源码观察 → 设计推理 → 边界」重新组织，代码片段尽量短，只保留能说明决定的几行。

需求篇：Agent 执行环境要满足什么

先把需求摊开。不然后面看到「为什么 Docker 只映射一个端口」「为什么暂停要提交镜像」「为什么出向策略默认拒绝」，会觉得是风格问题；其实每一条都在回答这里列出的某个约束。

一个教学场景

假设团队在做一个修 bug 的编码 Agent。它的典型工作循环是：

  1. 读一个仓库；
  2. 跑测试，看哪条失败；
  3. 改代码；
  4. 再跑测试；
  5. 把 diff 交回给人类审。

这个循环里有四种东西要被真实执行：shell 命令、文件读写、语言运行时（真正跑测试）、以及对外的网络访问（装依赖、查文档）。同时它有三个隐含要求：并行（一个团队同时跑几十个任务）、可清理（跑完就该消失）、不可信（模型写的代码可能 rm -rf /，也可能拿沙箱当跳板去打内网）。

这就是本书所有讨论的出发点。下面把需求拆成六条，每条都对应上游的一个具体机制。

需求一：隔离必须是运行时的性质，不是约定

「别删错目录」靠代码审查解决，「不能删到别人」只能靠隔离。容器名空间能挡住大部分误操作，但挡不住内核漏洞导致的逃逸。所以需求要写成可替换的层次：

  • 默认：标准容器（runc）。
  • 加强：用户态内核（gVisor）或轻量虚拟机（Kata，含 QEMU 与 Firecracker 两种）。
  • 极致：每个沙箱一台 microVM。

上游把这件事做成了服务端配置（[secure_runtime]，type 取 ""/gvisor/kata/firecracker），调用方不改代码。教学推演的理由很直接：隔离级别是运维对整台机器的承诺，不该让每个调用方各自决定，否则同一个集群里会混着不同强度的边界，审计时说不清。

需求二：创建要快，且快在「已经存在的容量」上

Agent 的交互是对话式的。用户等 30 秒才看到一个空沙箱，体验上等于失败。但「快」有两种做法，代价完全不同：

  • 把创建流程优化到极致：省掉不必要的 API 调用、并行拉镜像。
  • 让创建不创建：提前准备好容量，创建只是把容量认领出去。

上游两条都做了。Kubernetes 侧是 Pool：预热 Pod 池，分配是把 Pod 标注给某个 BatchSandbox，不再经过调度器。Fast Sandbox 侧更激进：模板预构建成 golden image，创建时恢复一份 vmstate 快照，而不是启动内核。

文档给的数字可以建立量级感：同一份 Performance 页里，Kubernetes 后端启用 Pool 后交付 100 个沙箱总耗时 0.92 秒；Fast Sandbox 在 ACK 两节点集群上的 SDK 创建 p50 是 64.0 ms（串行 100 次，预热后）。这两个数字的测量边界完全不同，不能互相替代，后面第 8 篇会专门讲怎么读它们。

需求三：沙箱里要有一套「能干活」的接口

隔离环境本身是个空壳。Agent 需要的是：执行命令并实时看到输出、后台跑长任务、上传下载文件、开一个交互终端、跑 Jupyter 内核、看 CPU/内存。这些不能靠「SSH 进去」解决，因为 SSH 是给人用的协议，没有结构化输出，也没法做细粒度权限。

所以需求是三件事：

  1. 一个数据面 API，覆盖命令、文件、PTY、代码执行、指标；
  2. 流式语义，输出要边跑边到，不能等命令结束；
  3. 明确的终止语义，让客户端能区分「跑完了」「失败了」「连接断了」。

第三条最容易被忽略。上游为此规定了 execution_complete 事件携带 exit_code，并且明确写了「流在终止事件之前结束，不能推出成功」。第 9 篇会拆这段。

需求四：沙箱要能被访问，但访问路径不能由调用方猜

沙箱里跑的服务（8080 的 web 应用、5900 的 VNC、8888 的 Jupyter）需要被外部访问。三种拓扑三种答案：单机 Docker 是宿主端口映射，Kubernetes 是 ingress 网关，两者都不通时是控制面反向代理。

如果让调用方自己拼地址，就出现两个问题：不同后端要写不同客户端代码；拓扑一变，所有调用方同时坏掉。所以上游把「怎么访问」也纳入契约：GET /sandboxes/{id}/endpoints/{port} 返回一个已经可用的地址加上必须携带的请求头。客户端不需要知道后面是 Docker 还是 Istio 还是自建网关。

这条需求的隐含代价：endpoint 解析必须便宜，因为它会被反复调用；而且它不能证明沙箱存在（Fast Sandbox 的路由是本地签名，不解引用就不查后端）。第 10 篇会讲这个「签发与就绪解耦」的选择。

需求五：出向流量默认拒绝，并且可解释

沙箱里的代码会访问外部世界：装 pip 包、调模型 API、拉 git 仓库。默认放开等于把生产网络的出口交给一段模型生成的代码。

需求因此变成三层：

  • 能按域名控制，因为运维想说的是「只允许 pypi 和 github」，不是「只允许 10.2.0.0/16」；
  • 能落到包级，因为只做 DNS 过滤时，一个已经解析出的 IP 可以绕过域名规则；
  • 平台能压过用户，因为租户策略不该能打开平台明令禁止的目标。

上游的实现是两条层：DNS 过滤 + nftables 默认拒绝，外加平台覆盖规则（deny.always / allow.always）与端口底线。第 11 篇拆。

还有衍生需求：Agent 需要调第三方 API，但密钥不能进沙箱。这变成了 Credential Vault（第 12 篇）：出向请求在沙箱外的代理里被加上凭据，沙箱进程只看到「已经认证好的流量」。

需求六：生命周期要比「创建/删除」更细

Agent 任务有长有短。短任务跑完就该消失；长任务在等人类回复时不该持续占 CPU；被中断的任务希望保留现场，下次接着跑。

于是需要四件事：

  1. 绝对过期，而不是空闲超时——否则重启会把 TTL 重置，寿命无法审计；
  2. 暂停/恢复，且恢复后沙箱 ID 不变；
  3. 快照，从运行中的沙箱做出可复用的起点；
  4. 访问即续期，让活跃会话不被 TTL 掐断。

上游同时提供「暂停」和「快照」两个概念，看起来重复，实际边界不同：暂停是内部机制，目的是释放算力、保留连续性；快照是公开产物，目的是把状态变成可复制的制品。第 13 篇会把这两个词分开。

非需求：明确不做的

需求文档的价值一半在「不做什么」。从 ROADMAP 与文档能读出几条克制的边界：

  • 不在生命周期 API 上做稳定的 v1 承诺。ROADMAP 的「Not Currently Planned」第一条就是不宣布稳定 v1，理由是对语义、运行时行为与 SDK 兼容性还不够成熟。
  • 不假装控制面已经水平扩展。默认部署是单活；PostgreSQL 只支撑一个很窄的多副本能力（快照创建协调），文档原话是「General load-balanced lifecycle HA is not supported yet — and is not pretended」。
  • 不把所有后端做成功能等价。模板只支持 Fast Sandbox；生命周期钩子只支持 Kubernetes 容器后端；Fast Sandbox 拒绝卷挂载与 credentialProxy。这些差异写进了 docs/api/implementation-compatibility.md，而不是用「即将支持」掩盖。
  • 不承诺沙箱文件系统持久。暂停/快照之外，容器可写层随 Pod 消失；文档明确说进程退出、OOM、驱逐、节点丢失都不会自动快照。

六条需求的相互关系

这六条不是并列的清单，它们互相拉扯：

  • 要快（需求二）就要预热容量，预热就与「每个请求定制环境」（需求四、六）冲突。上游的解法是把定制性从 Pod 挪到 task 与注解上。
  • 要强隔离（需求一）就要 microVM，microVM 与「每沙箱一个 sidecar」（需求五）冲突。上游的解法是每个 Fastlet Pod 一个共享 egress 进程，按 subject 分治。
  • 要可解释的出向策略（需求五）就要 L7 拦截，拦截就要在沙箱里装 CA，这又削弱了「沙箱不信任自己环境」的假设。上游的选择是默认关、开启时把 CA 装进系统信任库，并把配置面标为实验。

第 18 篇会把这些冲突集中算一遍账。现在只需要记住：后面每一个看起来奇怪的设计，都是某两条需求打架后的落点。

技术方案：一条契约、三种后端、两个平面

需求确定之后，方案的第一件事是划分边界。OpenSandbox 的划法可以用一句话概括：对外一条契约，对内三种后端，横向切两个平面。这一篇讲这三句话各自意味着什么，以及为什么不是别的划法。

一条契约

specs/ 目录下有四份 OpenAPI 文件，它们是公开契约的唯一来源：

文件 大小 服务的对象
sandbox-lifecycle.yml 约 120 KB 控制面：创建、查询、删除、续期、endpoint、暂停/恢复、快照、模板、网络策略
execd-api.yaml 约 119 KB 数据面：命令、文件、目录、代码上下文、指标、隔离会话
egress-api.yaml 约 26 KB 出向策略与凭证保管
diagnostic-api.yml 约 16 KB 诊断日志/事件描述符

四条契约分给三类进程：生命周期服务器实现第一、第四条；execd 实现第二条；egress 实现第三条。它们之间没有共享的 RPC，只有 HTTP 和「客户端先解析 endpoint，再直连」的约定。

这个选择有代价：客户端要理解三个不同的 base URL（默认分别是 8080、44772、18080），还要知道哪些操作在控制面、哪些在数据面。收益是边界非常硬——控制面的故障不会让正在运行的命令中断，反过来也一样。第 17 篇会把这条边界当作可用性讨论的基础。

三种后端

runtime.type 只有两个合法值：docker 和 kubernetes。第三种后端 Fast Sandbox 不是新的 runtime.type，而是 Kubernetes 模式下的一个组合分支。

runtime.type = "docker"
  └── DockerSandboxService         直接操作 Docker daemon

runtime.type = "kubernetes"
  └── CompositeSandboxService
        ├── KubernetesSandboxService   容器负载：BatchSandbox 或 agent-sandbox
        └── FastSandboxService         模板负载：microVM，经 FastPath 控制

路由规则写在 composite_service.py 里，短到可以整段引用：

def _backend(self, sandbox_id: str) -> KubernetesSandboxService | FastSandboxService:
    return self._fsb if sandbox_id.startswith("fsb-") else self._kubernetes

async def create_sandbox(self, request: CreateSandboxRequest) -> CreateSandboxResponse:
    if (request.template_id or "").strip():
        return await self._fsb.create_sandbox(request)
    if (request.snapshot_id or "").strip() and request.resolved_snapshot_backend == "fsb":
        return await self._fsb.create_sandbox(request)
    return await self._kubernetes.create_sandbox(request)

创建时看请求（有 templateId 走模板），之后看 ID 前缀（fsb- 走模板）。没有注册表，没有额外的数据库表，前缀就是分发器。这个做法在第 8 篇还会再讨论一次，因为它同时是这套设计最省事和最脆的地方。

两个平面

架构文档把交互路径分成三条：生命周期管理（橙）、执行与服务访问（蓝）、出向控制（绿）。落到进程上就是两个平面：

控制面只做四件事：认证、校验、持久化自己拥有的记录、把动作委派给运行时。

数据面做剩下的全部：命令执行、文件读写、PTY、Jupyter、指标，以及出向流量的 DNS 与包过滤。

中间那条线可以写成一条规则：控制面不碰沙箱内部，数据面不碰沙箱的帐。

这条规则解释了三个容易困惑的现象：

  • 为什么服务器不保存沙箱列表？因为容器、Pod、CR 才是事实来源（docs/architecture/control-plane/server.md 的原话是「Sandboxes are not rows in the server's database」）。
  • 为什么服务器要用代理转发流量？那不是主路径，是当直连和网关都不通时的兼容退路。
  • 为什么 execd 需要自己的令牌？因为控制面的 API key 只授权「管理沙箱」，不授权「进入沙箱」。

六条设计原则

上游在架构文档末尾列了设计原则，我认为其中四条真正约束了代码形状，值得逐条落到代码上：

Protocol First。 公开行为从 specs/ 开始。这条原则最直接的体现是：服务器代码里的 API_CONTRACT_VERSION 与 specs/sandbox-lifecycle.yml 的 info.version 对齐，而包版本另走 GET /version。契约版本和发布版本是两个东西。

Control Plane vs Data Plane。 上面已讲。

Secure Defaults with Explicit Escape Hatches。 默认要有 API key；非交互环境下没 key 直接拒绝启动，除非显式设置 OPENSANDBOX_INSECURE_SERVER=YES。多租户开启时，启动阶段就要校验所有租户命名空间可达，否则不接流量。这条「启动即失败」比「请求时失败」强的理由是：隔离配置错了，单看某个请求是看不出来的。

Observable Failures。 沙箱状态不只有 state，还有 reason、message 和状态迁移时间。execd 有 metrics，服务器有 diagnostics，ingress/egress 有连接分类与拒绝计数。第 16 篇会讲这套可观测性的形状。

为什么不是别的划法

有三个看起来更简单的方案，值得说明它们为什么不在这里：

方案 A：把执行 API 合进生命周期服务器。 这样只有一个 base URL，客户端最简单。代价是命令的 SSE 流会穿过控制面，控制面升级或重启就会打断正在跑的任务；而且所有沙箱的命令流量都要过服务器，带宽和连接数都成了控制面的问题。上游选了分离，把「流」留在数据面。

方案 B：把三种后端做成三个独立产品。 这样每套可以按自己的语义优化。代价是 SDK 要写三份，用户体验碎片化，而且「本地 Docker 起步、上线换 K8s」这条最常见的迁移路径会失效。上游选一个接口 + 组合路由，代价是必须接受「某些功能只有某些后端支持」。

方案 C：用 Kubernetes 一种后端覆盖全部。 这样可以少维护一套 Docker 实现。代价是本地开发必须装集群，而 README 的第一句引导就是 uvx opensandbox-server + Docker。上游保留 Docker 作为一等公民。

三个方案都不是错的，只是各自把复杂度放在了不同地方。OpenSandbox 把复杂度放在了「运行时适配层」和「文档里的兼容性边界」上——这是最不影响调用方、但最考验维护者的位置。

本章要点

  • 四份 OpenAPI 契约分给三类进程，控制面与数据面之间没有 RPC。
  • runtime.type 只有 docker 与 kubernetes；模板沙箱是 Kubernetes 模式下的组合分支，用 fsb- 前缀分发。
  • 控制面不碰沙箱内部，数据面不碰帐；因此服务器不保存沙箱列表。
  • 运行时中立只到 API 形状，能力差异必须显式声明。
  • 三条被放弃的替代方案，各自把复杂度放在了别处。

契约层：四份 OpenAPI 与它们没写的东西

读一个平台，先读它的契约。契约决定了所有调用方能看到的世界，也决定了实现者能偷偷改多少东西。

OpenSandbox 把 specs/ 当作公开行为的唯一来源，并把这句话写进了 AGENTS.md：生成物要从源头重新生成，而不是只打补丁。这一篇按使用者的顺序读这四份文件：先看生命周期契约怎么描述一个沙箱，再看数据面契约怎么描述一次执行，最后看它们各自没写什么。

生命周期契约的骨架

specs/sandbox-lifecycle.yml（info.version: 0.1.0）的 base path 是 /v1，资源分成四组：

组 端点 语义
沙箱 POST/GET /sandboxes、GET/DELETE /sandboxes/{id} 创建、列举、查询、删除
状态 POST .../pause、.../resume、.../renew-expiration、PATCH .../metadata 中间态操作与非生命周期字段
访问 GET .../endpoints/{port}、/networkpolicy、/credential-vault 让调用方能进得去、管得住
派生资源 /snapshots、/templates 从沙箱派生的可复用制品

创建请求的字段在 api/schema.py 里能看全，一共十五个左右，可以按用途分四类：

来源       image / snapshotId / templateId        （三者互斥）
形状       platform / resourceLimits / resourceRequests / volumes
行为       entrypoint / env / lifecycle / networkPolicy / credentialProxy
元数据     metadata / extensions / secureAccess / timeout

这份字段表里有两处很能说明设计取向。

第一处是 extensions 是 map<string,string>，不是结构化字段。它给了平台一个不破坏契约的扩展槽：例如访问续期的旧式写法 extensions["access.renew.extend.seconds"] 在 1.x 期间继续支持，新代码应该用 lifecycle.renewalPolicy（OSEP-0009）。把「过渡期」写进契约而不是写进代码注释，是这份契约比较成熟的一面。

第二处是 resourceLimits 用 RootModel[Dict[str,str]]，值是字符串而不是数字：{"cpu": "500m", "memory": "512Mi", "gpu": "1"}。这样 Kubernetes 的数量表达式可以原样传，Docker 后端再自己换算。代价是校验变弱——"500M" 和 "500m" 在语义上不同，契约层不管。

状态与错误：把「不确定」编码进去

沙箱对象里最关键的不是 image，而是 status：

status.state         Pending / Running / Pausing / Paused / Resuming / Stopping / Terminated / Failed
status.reason        机器可读的原因码
status.message       人能读的说明
status.lastTransitionAt  最近一次迁移时间

四个字段合起来解决了一个常见问题：客户端拿到 Failed 时，需要知道是「镜像拉不到」还是「节点资源不足」，而不是只有一句「创建失败」。

错误响应的形状是 ErrorResponse{code, message}，HTTP 状态码承担粗分类：400 请求非法、401 认证失败、404 不存在、409 状态冲突（比如对已暂停的沙箱再暂停）、429 容量耗尽、503 暂不可用。文档里还有一条容易被忽略的补充：不同后端对「不支持」用的状态码并不统一（模板管理在 Docker 上返回 501，快照服务的不支持运行时会返回 409 预检，隔离会话的 diff/commit 返回 503）。兼容性文档明确说这不是缺陷而是现状，并提醒「不要假设有一个统一的不支持状态码」。

异步创建：202 与轮询

创建是异步的：API 立刻返回，沙箱先处于 Pending，客户端轮询 GET /sandboxes/{id} 或使用 SDK 的就绪帮助函数。这一点在契约里就定了，因为 Pod 调度和 microVM 启动都可能耗时数秒。

为什么不用长连接或回调？文档给的理由是「不能让 HTTP 请求一直挂在那儿」。教学推演上还有两条：长连接在网关处容易被超时掐断；回调需要一个所有调用方都能被访问的回调端点，而调用方经常在自己都进不去的网络里。

异步的代价是状态机必须严谨。第 13 篇会看到它严谨到什么程度：连 Paused 之后 Pod 还没删完这段窗口，都要在文档里写清楚「可以提交 resume，控制器会等旧 Pod 消失」。

endpoint：一个被低估的端点

GET /sandboxes/{id}/endpoints/{port} 返回的是一个对象，不是字符串：

{
  "endpoint": "http://10.0.0.12:44772/proxy/8080",
  "headers": { "X-EXECD-ACCESS-TOKEN": "..." }
}

这个形状是刻意的。如果只返回地址，调用方就得自己知道要带什么头；而「要带什么头」恰恰随部署变化（secure access 的签名、egress sidecar 的认证、execd 的访问令牌）。把地址和头打包返回，客户端就能写一行代码适配所有拓扑。

还有一个细节藏在响应头里：解析 endpoint 时服务器会回 OPEN-SANDBOX-ORIGIN，模板来源的沙箱明确标成 template。SDK 用这个信号决定后续的策略操作走生命周期 API 还是走 sidecar——这是第 8 篇的关键分支。

数据面契约：SSE 不是传输细节

specs/execd-api.yaml 描述的是沙箱内 API，base URL 默认 http://localhost:44772。它的核心不是路由表，而是流的事件模型：

init / status / stdout / stderr / result / execution_complete / execution_count / error / ping

ServerStreamEvent 在 Go 里的字段很少：type、text、exit_code、execution_time、timestamp、results、error。少是有意的：事件越简单，跨语言客户端越容易正确实现。

契约里写得很清楚的三条语义，值得单独抄出来：

  1. 行尾保留原样。stdout 事件里的文本保留 \n、\r 或 \r\n，客户端按序拼接就能还原输出，最后一个事件可能是不完整的一段。
  2. 成功也有退出码。前台 POST /command 以 execution_complete 携带 exit_code: 0 结束；后台启动确认与代码执行事件里没有这个字段，缺失不代表成功。
  3. 流提前结束不构成成功。在终止事件之前断流，只能当作不确定。

第 9 篇会讲为什么这三条要写进契约，而不是留给 SDK 猜。

契约没写的东西

这是本章最重要的部分。上游自己在 docs/api/implementation-compatibility.md 里列了一份清单，说明「契约覆盖」和「实现能力」不是一回事：

  • PTY 路由不在 OpenAPI 里。 execd 的 /pty HTTP 与 WebSocket 路由已经实现，但还没进 execd-api.yaml。文档的结论很直接：不能从「OpenAPI 兼容」推出「支持这类扩展」。
  • 隔离会话的 diff/commit 在契约里但没实现。 两个端点都在 execd-api.yaml 里，当前实现返回 503，并且 /v1/isolated/capabilities 会如实报告 diff_supported: false。这是「契约先行」的必然产物，处理方式是显式失败而不是假装成功。
  • 能力随运行时不同。 模板只在 Fast Sandbox 上支持；生命周期钩子只在 Kubernetes 容器后端支持；Fast Sandbox 拒绝卷挂载。这些差异写进了兼容性文档的表格，而不是靠版本号掩盖。
  • 没有统一的能力协商端点。 文档明确说当前没有通用的 capability negotiation，也没有一套 v1 一致性档位。调用方要么按操作逐个探测，要么按文档声明。

我在这里读出两个判断。第一，这个项目宁愿把不一致写进文档，也不愿造一个假的统一层——短期难看，长期可信。第二，/v1/isolated/capabilities 这种「按特性探测」的局部机制比全局协商更现实：不同子系统的成熟速度本来就不同。

SDK 是契约的消费者，不是契约

五种语言（Python、JavaScript/TypeScript、Java/Kotlin、C#/.NET、Go）的沙箱 SDK 都建在 specs/ 上：生成代码处理普通请求响应，手写层处理流式、传输生命周期、错误映射和高级模型。这个分工在架构文档里写得很直白。

所以 SDK 的行为不构成契约。兼容性文档专门用一节列出「当前 Python SDK 的 endpoint 期望」：create() 会先解析 44772（execd）再解析 18080（egress），create_from_template() 只解析 44772，connect() 两者都要。作者提醒这是「当前树的描述，而不是可移植的协议要求」。

对自建后端的读者，这一节的价值是：你可以只实现一个窄的操作集，但必须知道高层的 SDK 流程会先做哪些查找。只实现生命周期 API 加上自己的 workload 客户端，也是一条合法的集成路径——只要你不用官方 SDK 的 Sandbox 类。

本章要点

  • 四份契约分给三类进程；生命周期契约的 base path 是 /v1，契约版本 0.1.0 与包版本是两件事。
  • extensions 是刻意留的字符串扩展槽，用来承载过渡期语义。
  • 异步创建 + 四字段状态 + 结构化错误，是「让失败可解释」的最小组合。
  • endpoint 返回地址和请求头，因为访问方式随部署而变。
  • SSE 的行尾保留、成功退出码、断流不等于成功，三条语义写进了契约。
  • 契约覆盖不等于实现能力：PTY 不在契约里，diff/commit 在契约里但没实现，能力按后端不同。

控制平面：一台 FastAPI 服务器的四条不变量

server/ 里约 8.4 万行 Python，但真正定义它的只有四条不变量。后面所有代码都是在守住这四条。

分层与它的规则

目录结构很规整：

server/opensandbox_server/
  main.py          启动、中间件、路由注册、运行时校验
  api/             路由与 schema（lifecycle 618 行、proxy 776 行、schema 1817 行）
  middleware/      auth、request_id、date_header、http_metrics
  services/        生命周期状态机与运行时集成（docker/、k8s/、fast_sandbox/）
  repositories/    只持久化服务器自己拥有的记录（snapshots/、templates/）
  tenants/         身份提供方：从 API key 解析出租户
  integrations/    renew_intent、idle_pause、otel

架构文档把规则写成两条，我认为可以拆成四条更可检查的不变量。

不变量一：API 层不直接碰运行时

所有路由都只调用 SandboxService 接口。api/lifecycle.py 的创建路由一共不到 30 行有效逻辑：

async def create_sandbox(request: CreateSandboxRequest, x_request_id: ... ) -> CreateSandboxResponse:
    validate_extensions(request.extensions)
    validate_renew_policy_conflict(request.lifecycle, request.extensions)
    normalize_network_policy_actions(request.network_policy)
    if not (request.template_id or "").strip():
        request = await resolve_sandbox_image_from_request(request)
    return await sandbox_service.create_sandbox(request)

四步校验加一次委派。没有 if runtime == "docker"，没有 Docker 客户端对象，也没有 Kubernetes API 调用。

这条不变量的收益不只是「可替换后端」。它让 API 层变成了一个纯函数式的边界：给定请求，产出一组校验结果和一次服务调用。测试可以只 mock 服务接口，不需要 Docker daemon。

代价是抽象必须足够通用。extensions 之所以是 map<string,string>，一部分原因就在这里：如果每个后端都要在自己的字段上做定制，接口就抽象不住了。

不变量二：沙箱不是数据库里的一行

服务器只持久化两类东西：

  • 快照元数据（repositories/snapshots/）
  • 模板目录（repositories/templates/）

沙箱本身不在库里。Docker 容器、Kubernetes 的 BatchSandbox/Pool、sandbox.fast.io 的 CR 才是事实来源。服务器每次读沙箱，都是去问运行时。

这个决定的直接后果是「服务器的存储后端可以随时换」：SQLite（默认 ~/.opensandbox/opensandbox.db）或 PostgreSQL，通过 [store] 切换。反过来说，如果沙箱是数据库行，换存储就等于数据迁移，而数据迁移必然带来停机窗口。

后果之二是重启后的行为。服务器重启时不需要恢复沙箱列表，只需要恢复两类附加状态：

  • Docker 后端的过期定时器（从容器标签里读回创建时间，重建 timer）；
  • 暂停/恢复中的状态（~/.opensandbox/metadata/_transition/ 下记录主容器状态与时间戳）。

createdAt 的处理很讲究：创建响应里的 createdAt 会写进容器标签 opensandbox.io/created-at，后续读取复用它；老容器没有这个标签，就退回 Docker 的创建时间。这是「事实来源在运行时，但服务器要保证语义一致」的典型手法。

不变量三：失败要发生在启动，不是请求

main.py 的 lifespan 里有一串会直接 os._exit(1) 的检查：

api_key_confirm(...)                    没配 API key → 交互式输入 YES 或环境变量 YES，否则退出
validate_tenant_config(...)             租户配置不合法 → 退出
validate_tenant_namespaces_on_startup   多租户命名空间不可达 → 退出
validate_secure_runtime_on_startup      声明的安全运行时不可用 → 退出

startup_guard.py 里的 api_key_confirm 是这个思路最清楚的一个实现：它不只看「有没有 key」，还区分场景——有 TTY 时需要人工输入 YES（30 秒超时），没有 TTY 时要求 OPENSANDBOX_INSECURE_SERVER=YES 显式承认。

架构文档给的理由是：隔离配错时，单个请求看不出来。 少一个 API key，每个请求都会成功，直到某个租户读到别人的东西。这种错误必须在启动时炸掉。

这条不变量的实现方式值得抄：把「不安全配置」写成一组启动期断言，每个断言都有一个明确的环境变量开关。这样运维能看到全部开关，而不是散落在代码里的 if。

不变量四：状态机只在这里定义

resume() 是暂停态操作，不是通用重启——这句话在 server.md 里写得很直接：已经退出的沙箱是 Terminated 或 Failed，诚实的答案是换一个新的，而不是悄悄复活。

于是状态迁移被限制成两条主路径：

创建：  Pending → Running
暂停：  Running → Pausing → Paused → Resuming → Running
结束：  Running → Stopping → Terminated
异常：  任意 → Failed（带 reason/message）

SandboxStatus 只有 state、reason、message、lastTransitionAt。文档特别提了一句实现细节：服务器管理的暂停/恢复转换会把主容器状态与时间戳写到 ~/.opensandbox/metadata/_transition/，重启后如果记录里的状态与观测到的容器状态一致才采用这个时间戳；不一致就丢弃。这是「持久化的是推导结果，采用前必须验证」的做法。

校验放在哪里

services/validators.py 有 723 行，比很多后端服务都长。校验被集中在一处，而不是散在路由和后端里，理由有三条：

  1. 同一个字段在不同后端要校验的规则不同（例如 networkPolicy 与 poolRef 不能同时出现），集中才看得全；
  2. 校验顺序本身是语义（先查 extensions 冲突，再解析镜像），集中才能固定顺序；
  3. SDK 不强制某些上限（例如 lifecycle 钩子的 timeoutSeconds 范围），服务器是最终权威——文档原话是「Server is the authority for request validation」。

代理层：不是主路径，但要正确

api/proxy.py 有 776 行，是 api 目录里最大的一块。它实现的 GET /sandboxes/{id}/proxy/{port} 是当「直连」和「网关」都不可用时的兼容退路。

代理层的正确性要求比想象中高，因为流量里可能带着凭据。文档列出几条具体规则：

  • 去掉逐跳头（hop-by-hop）和后端的 Server 头；
  • 保留后端的 Date，没有才补当前时间；
  • 只把以单个 / 开头的 Location 重写到同一沙箱的代理路由下，绝对 URL、//host/path 和普通相对路径原样转发；
  • HTTP 与 WebSocket 都支持；
  • 响应声明为 200 + default，因为 payload 由沙箱里的服务决定。

第三、四条合起来说明一个判断：代理不能自作聪明。跟随重定向、改写绝对地址、重新编码响应体，都会把「代理」变成「会改语义的中间件」，一旦出错就很难定位。宁可少做一点。

单活、双活与它们之间的窄门

服务器的默认部署是单活：一个副本、SQLite、升级时短暂中断。文档对这个边界的表述非常克制。

PostgreSQL 打开的不是「水平扩展的 API」，而是一个很窄的能力：两个副本协调公开快照创建。实现上没有用 lease 或 leader election，而是利用两个已有不变量：

  1. 先观察再创建：SandboxSnapshot 的 CR 名是确定性的，副本先查再建，撞上 409 AlreadyExists 当作成功；
  2. 终态写入用 CAS：数据库终态写入以期望的前一状态为条件，两个副本同时完成时一个赢、另一个空操作；
  3. 恢复扫描：崩溃副本留下非终态行，存活副本定期重扫，通过同一套 CR 观察推进。

文档明确声明「不声称跨数据库、Kubernetes 与镜像仓库的 exactly-once」，恢复间隔决定的是接管延迟，不是原子性。这段描述的价值在于它承认了什么没做到——第 17 篇会把它和「系统级 HA 仍在 ROADMAP」放在一起看。

一个请求在控制面里的完整路径

把上面的拼起来，POST /v1/sandboxes 的路径是：

HTTP 请求
  → RequestIdMiddleware       生成/透传 request id
  → AuthMiddleware            校验 OPEN-SANDBOX-API-KEY，解析租户
  → 路由 api.lifecycle.create_sandbox

同步返回 Pending 是关键：从这一刻起，客户端拿到的唯一事实来源是 GET /v1/sandboxes/{id}。控制面不再持有这个请求的任何状态，也不会因为后续的 Pod 调度失败而「记住」什么——失败写在沙箱对象的状态里。

本章要点

  • 四条不变量：API 不碰运行时、沙箱不在库里、不安全配置启动即失败、状态机只在控制面定义。
  • 服务器只持久化快照元数据与模板目录，因此存储后端可换。
  • 校验集中在 validators.py，服务器是最终权威。
  • 代理层刻意少做事：不改写绝对地址、不跟随重定向。
  • 默认单活；PostgreSQL 只支撑「两个副本协调快照创建」这一窄场景，文档不夸大它。

运行时路由：一个接口装下三种后端

第 4 篇说「API 层不碰运行时」。那么运行时到底是什么形状？答案是 SandboxService 这个抽象类，它定义了 13 个方法。

接口全貌

get_endpoint
get_sandbox_log_diagnostics    get_sandbox_event_diagnostics

前八个是生命周期，第九个是访问，后四个是诊断。这个划分本身就说明了一件事：接口是按「调用方能做的事」组织的，不是按后端实现组织的。诊断能进入接口，是因为运维和 AI 排障需要它，而不是因为 Docker 恰好有 docker logs。

接口里还有两个非抽象成员值得注意。一个是 set_tenant_provider，默认空实现（非 Kubernetes 后端不需要）；另一个是 close，用于释放后台 reader 和连接。两者都是「可选能力」——这暗示了抽象类的一个现实：接口能统一签名，统一不了依赖。

工厂：四行决定三个后端

implementations = {"docker": DockerSandboxService, "kubernetes": KubernetesSandboxService}
if selected_type not in implementations:
    raise ValueError(...)
if selected_type == "kubernetes":
    implementation = KubernetesSandboxService(config=active_config)
    return CompositeSandboxService(implementation,
        FastSandboxService(active_config, k8s_client=implementation.k8s_client))
return implementations[selected_type](config=active_config)

三个细节：

  1. runtime.type 的取值集合只有两个，Fast Sandbox 不在这里注册。
  2. FastSandboxService 复用 KubernetesSandboxService 已经建好的 k8s_client，不重复建连。
  3. 不认识的类型直接抛错，不在启动后降级。

第 3 点是第 4 篇「启动即失败」原则在小处的复现：配置写错了，进程根本起不来。

组合路由器：前缀即分发

CompositeSandboxService 把两个实现合成一个，规则只有两条：

def _backend(self, sandbox_id):
    return self._fsb if sandbox_id.startswith("fsb-") else self._kubernetes

async def create_sandbox(self, request):
    if (request.template_id or "").strip():
        return await self._fsb.create_sandbox(request)
    if (request.snapshot_id or "").strip() and request.resolved_snapshot_backend == "fsb":
        return await self._fsb.create_sandbox(request)
    return await self._kubernetes.create_sandbox(request)

创建时看请求来源，之后看 ID 前缀。文档给的理由是「没有新的公开 API，也没有沙箱到后端的注册表」。

这个设计的优点很实在：零状态。不需要一张「sandbox → backend」的表，也就不需要维护它的一致性、不需要在切换后端时迁移。第 17 篇讨论故障恢复时会看到它的好处：控制面崩溃重启后，路由信息仍然在 ID 里。

缺点也同样实在：

  • 前缀是硬编码的知识。任何知道 fsb- 含义的代码都成了隐式耦合点，包括 SDK（它通过 OPEN-SANDBOX-ORIGIN 头而非前缀来判断，但行为要一致）。
  • 前缀不能表达第三个后端。如果将来出现第四种运行时，要么再挑一个前缀，要么改成真正的注册表。
  • 前缀由谁生成必须严格约束。上游的做法是每个后端自己生成 ID，模板后端加 fsb- 前缀；一旦某个后端漏了前缀，路由会静默走错分支——这不是崩溃，是错误的行为，更难查。

我倾向于把它看成一次有意识的取舍：在只有两个分支的时候，前缀分发比注册表省下的复杂度是真实收益；当分支增长到三个，这笔账要重算。

快照的跨后端路由

创建请求里还有一个不显眼但重要的分支：snapshotId 走哪个后端？

答案不是「根据当前 runtime 猜」，而是问快照记录。CreateSandboxRequest 里有一个私有属性 _resolved_snapshot_backend，在路由之前由 resolve_sandbox_image_from_request 从快照行里读出 restore_config.backend。这样「这个快照是谁做的」由数据决定，而不是由当前部署的配置决定。

这条规则的必要性在于：快照是持久制品，可能产生于另一个后端或另一次部署。Docker 做的快照是本地 OCI 镜像，Kubernetes 做的是推送到 registry 的镜像，Fast Sandbox 做的是内容寻址的 artifact set。三者的恢复路径完全不同，靠猜一定会猜错。

不支持的功能怎么失败

接口统一之后，最危险的情况是「方法存在但后端不支持」。上游的处理是按操作返回明确错误，而不是编造成功：

场景 状态码
Docker 上使用模板管理 501

Fast Sandbox 上带 credentialProxy.enabled 或卷挂载创建 请求被拒绝（adapter 明确拒绝）

文档承认「没有统一的不支持状态码」，并把这当成需要显式文档化的现状。我认为这是对的选择：统一成一个状态码会让调用方无法区分「这个后端不支持」「你没权限」「暂时不可用」——而这三种情况应该触发完全不同的客户端行为（换后端 / 换凭据 / 重试）。

后端内部的适配层

抽象接口不覆盖的差异，被压进各后端自己的目录里。几个典型例子：

Docker 的 Windows 特化。 services/docker/windows_profile.py 单独处理 Windows 容器的差异：环境变量名大小写不敏感、批处理文件需要 shell 语法、文件权限语义不同。这些没有污染接口。

端口的分配与回收。 services/docker/port_allocator.py 负责在非 host 网络模式下分配宿主端口。这是 Docker 独有的概念（Pod 没有「宿主端口映射」），所以它只存在于 Docker 目录里。

安全运行时的解析。 services/runtime_resolver.py 把服务端配置翻译成后端参数：

DEFAULT_DOCKER_RUNTIMES = {"gvisor": "runsc", "kata": "kata-runtime"}
DEFAULT_K8S_RUNTIME_CLASSES = {"gvisor": "gvisor", "kata": "kata-qemu", "firecracker": "kata-fc"}

同一份 [secure_runtime] type = "kata" 配置，在 Docker 上变成 --runtime kata-runtime，在 Kubernetes 上变成 runtimeClassName: kata-qemu。调用方完全看不到这个差异——它连字段都没有。

Kubernetes 的工作负载 provider。 kubernetes.workload_provider 可取 batchsandbox（默认，自有 CRD）或 agent-sandbox（kubernetes-sigs/agent-sandbox）。这是「同一后端下的两种实现」，比「三个后端」更细一层。上游没有把它做成两个 runtime.type，理由大概是：客户端不该关心集群里装的是哪套 CRD。

抽象够不够

用一次思想实验检验这个接口：如果要接第四种后端（比如本地 microVM 或者一台远程 SSH 主机），需要改什么？

  • 实现 13 个方法；
  • 提供一个 ID 生成规则，最好带前缀；
  • 在 factory.py 注册，或者扩展 Composite 的分支；
  • 在 docs/api/implementation-compatibility.md 里写清哪些能力不支持。

不需要改 API、schema、SDK。这说明抽象的形状是对的。

但也有一条暗线：endpoint 的语义。接口只要求返回一个 Endpoint，没有约束它「必须直连」「必须支持 WebSocket」「必须能带自定义头」。这些差异被写在了文档里，而不是类型里。类型系统无法表达「这个后端返回的 endpoint 不支持任意 TCP 转发」——第 10 篇会看到这条限制的实际后果。

本章要点

  • SandboxService 有 13 个方法：8 个生命周期、1 个访问、4 个诊断，按调用方能力而非后端实现组织。
  • 工厂只认两个 runtime.type，Fast Sandbox 是 Kubernetes 模式下的组合分支。
  • 前缀分发换来零状态路由，代价是隐式耦合和「不能表达第三个后端」。
  • 快照创建走哪个后端由快照记录决定，不由当前配置决定。
  • 不支持的功能按操作返回 501/409/503，不编造成功。
  • 后端差异被压进各后端目录，接口只保留跨后端的形状。

Docker 后端：一个宿主端口装下整个容器

单机 Docker 是最容易被低估的后端。它没有调度器、没有 CRD，看起来只是「调 Docker API 建个容器」。但要在同一台机器上同时跑几十个沙箱、每个沙箱里跑着任意多个服务，还要让它们都能被访问，需要解决一个具体问题：端口的组合爆炸。

这一篇就从这个端口问题开始。

问题：一个沙箱里有多少个端口

假设每个沙箱要暴露 8080（应用）、5900（VNC）、8888（Jupyter）、44772（execd）。如果每个容器端口都映射到宿主，那么 30 个沙箱需要 120 个宿主端口，还要保证不冲突、要维护防火墙规则、要在容器重建后重新分配。而且——这是最关键的——端口的数量由用户镜像决定，服务器事先不知道。

OpenSandbox 的解法是：每个沙箱只映射一个宿主端口。

一个端口的路由原理

execd 内置了一个轻量反向代理。所有发往 /proxy/{port}/... 的请求，被转发到同一容器内的 127.0.0.1:{port}。

于是端到端路径变成：

浏览器  →  host:40xxx/proxy/8080/app   →  execd (44772)  →  127.0.0.1:8080/app
         →  host:40xxx/proxy/5900       →  execd          →  127.0.0.1:5900

服务器只绑定 execd 的代理端口（容器内 44772），并给它打上标签 opensandbox.io/embedding-proxy-port。调用方通过 get_endpoint(..., port=8080) 拿到 {public_host}:{host_proxy_port}/proxy/8080。

三个后果值得单独说：

端口冲突消失。 每个沙箱一个宿主端口，机器上能放的沙箱数量由端口范围和资源决定，而不是由每个沙箱暴露多少服务决定。

协议自动兼容。 代理保留 Upgrade、Connection 等头，所以 HTTP、SSE、WebSocket 共用同一个映射，不需要为 VNC 或终端额外开洞。这一条直接决定了浏览器里的远程桌面能用。

防火墙规则简化。 只需要对一段宿主端口开口，而不是每个沙箱的每个服务。

还有一个可选的第二映射：opensandbox.io/http-port，给 8080 一个「不含 /proxy/ 前缀」的常规 HTTP 入口。这是为那些不能处理路径前缀的客户端准备的——比如某些 aio-sandbox 镜像自带 API，它不知道 /proxy/8080 是外挂的路径。

什么时候绕过代理

代理不是唯一路径。get_endpoint(..., resolve_internal=True) 会返回容器的 Docker 网络 IP（例如 172.17.0.3:5900），跳过宿主映射。

但文档给了一条很实际的警告：服务器跑在容器里，不等于它能路由到沙箱。一个接在 Compose 网络上的服务器，默认无法访问 Docker 默认 bridge 上的容器。所以「内部地址」只在调用方确实在同一网络中时可用。

这条限制导致了一个配置陷阱，文档专门写了一整节：当服务器容器通过挂载的 socket 在默认 bridge 上创建沙箱时，需要

[proxy]
resolve_internal = false

[docker]
network_mode = "bridge"
host_ip = "host.docker.internal"

并且服务器容器要能解析 host.docker.internal（Linux 上需要 extra_hosts: ["host.docker.internal:host-gateway"]）。文档还补了一句历史教训：旧的 server/v0.2.3 镜像把内部 IP 解析硬编码在两条代理路径里，设置 resolve_internal = false 也救不回来，SDK 的就绪检查会超时。修完之后必须拉新镜像并重建容器。

这段的价值不在配置本身，而在于它示范了「兼容性事实也要写进文档」：一个已经修掉的老版本的坑，仍然值得保留，因为生产环境里还跑着老镜像。

网络模式与它们各自的代价

模式 行为 代价
bridge（默认） 独立桥接网络，只映射代理端口 需要端口分配；networkPolicy 只用这个模式
host 共享宿主网络栈 实际只能一个沙箱一台机，除非手工错开端口
none 无网络 只能离线跑代码
pasta / slirp4netns 用户态网络（podman rootless） 没有宿主可路由的容器 IP，只能走映射端口
自定义网络名 用户定义的 Docker network 需要网络已存在，启动时校验

networkPolicy 只在 bridge 下支持，代码里是显式拒绝的（networkPolicy is not supported when docker network_mode=host）。原因不难推：egress sidecar 需要和沙箱共享网络命名空间并使用 iptables/nftables，用户态网络模式下没有可用的 bridge 与 netfilter 路径。

用户态模式还有一个细节容易被误解：这类模式下 docker inspect 返回的 NetworkSettings.IPAddress 是空的，Networks 也没有条目。所以 resolve_internal=True 在这类模式下不会报错，而是回退到宿主映射地址——和「共享 egress sidecar 网络命名空间」时的回退一致。这是「让 API 保持可用而不是给一个无意义的错误」的选择。

execd 是怎么进容器的

沙箱镜像是用户给的，里面没有 execd。所以运行时要做一次注入：

  1. 从 [runtime].execd_image 里把 execd 二进制暂存到沙箱容器；
  2. 安装一个 bootstrap 启动器；
  3. 由 bootstrap 启动用户 entrypoint。

文档把这个过程描述为「staging」，代码在 services/docker/container_ops.py。第 9 篇会从 execd 的视角再看同一件事：execd 可以当 init（execd --init），也可以只做旁挂守护进程，两种模式的启动顺序不同。

注入式的好处是镜像不需要为 OpenSandbox 定制；坏处是每次创建都要复制二进制，并且镜像里必须有 cp/tar 之类的工具。这也是为什么 Fast Sandbox 走另一条路：模板构建时就把 execd 烘进 guest 镜像，创建时不需要注入。

生命周期操作的具体含义

Docker 后端把抽象方法翻译成容器操作，其中有两个容易被问到的点。

暂停的顺序。 有 egress sidecar 时，暂停先冻结沙箱主容器，再冻结 sidecar；恢复先解冻 sidecar，再解冻主容器。理由很直接：主容器一旦解冻就会发网络请求，此时 sidecar 必须已经在工作，否则第一批包会被丢掉或被默认策略拒绝。

删除与冲突。 文档明确了并发请求的映射：删除正在进行中、或容器已不在暂停/恢复所需状态时返回 409；主容器不存在返回 404。而 sidecar 相关失败、回滚失败保留 500。这个分级说明作者把「用户操作冲突」和「系统内部错误」严格分开了。

快照：commit 成本地镜像

Docker 的公开快照 API 实现是 docker commit：把运行中的容器提交成本地 OCI 镜像，然后从该镜像创建新沙箱。

这带来两个性质：

  • 快照是本地制品，不推送 registry，所以只在这台机器上可恢复；
  • 快照包含 rootfs，不包含内存，所以恢复的是文件系统，不是进程现场。

对比一下 Kubernetes 后端（提交镜像并推送到 registry）和 Fast Sandbox（检查点包含 rootfs + vmstate + memory），三种后端的「快照」语义强度完全不同。这也是第 3 篇强调「契约里有这个操作，不等于所有后端语义一致」的实例。

一个被隐藏的目录：定时器

创建时带 timeout 的沙箱会有一个过期定时器。服务器重启后，这些定时器需要重建——否则沙箱会永远活着。

Docker 后端的做法是从容器标签读回 createdAt，重新计算剩余的 TTL 并重建 timer。这看上去是个小细节，但它是「沙箱不在数据库里」这条不变量的直接成本：既然服务器不存沙箱列表，那就只能从运行时反查，而反查需要运行时上有可读的元数据。

于是容器标签成了半个数据库：

标签 用途
opensandbox.io/created-at 过期计算与响应一致性
opensandbox.io/embedding-proxy-port endpoint 解析
opensandbox.io/http-port 可选的直连 HTTP 映射
opensandbox.io/egress-sidecar-for sidecar 与主容器的关联
opensandbox.io/volume-managed-by 卷归属，避免误删别人的卷

这也解释了为什么 metadata 里有保留键校验：用户不能写 opensandbox.io/ 前缀的键，否则会和这些内部标签冲突。

本章要点

  • Docker 后端每个沙箱只映射一个宿主端口，其余端口通过 execd 的 /proxy/{port} 转发；HTTP/SSE/WebSocket 共用同一映射。
  • resolve_internal 只在调用方确实能路由到容器网络时可用；容器化的服务器需要 resolve_internal=false + host_ip。
  • networkPolicy 只在 bridge 模式生效，其他模式显式拒绝。
  • execd 由运行时注入，bootstrap 负责启动顺序；这是镜像可定制的代价。
  • 快照是本地镜像，含 rootfs 不含内存。
  • 容器标签承担了「半个数据库」的角色，包括过期重建与 endpoint 解析。

Kubernetes 后端：BatchSandbox 与恒定时间交付

Docker 后端回答的是「一台机器上怎么放很多沙箱」。Kubernetes 后端要回答的是另一个问题：在集群里，创建沙箱的延迟里有多少是调度器的？

答案不低。创建一个带调度约束的 Pod，要经过 API server 写入、调度器决策、kubelet 拉镜像、容器启动、就绪探针。这条链路的每一段都可能失败或变慢，而 Agent 场景希望创建是一次「认领」，不是一次「部署」。

OpenSandbox 的 Kubernetes 后端因此分成两层：一个标准的 operator（三个 CRD + 三个 reconciler），和一条预热池路径（Pool）。这一篇讲这套设计，重点是池子的容量模型，因为它决定了「快」是怎么来的。

三个 CRD

CRD 作用 关键字段
BatchSandbox 描述一个或多个相同沙箱 replicas、template、poolRef、expireTime、pause、taskTemplate
Pool 维护预热 Pod 的容量 template、capacitySpec、scaleStrategy、recycleStrategy
SandboxSnapshot 暂停/恢复与公开快照的记录 目标 BatchSandbox 名；状态里带镜像 digest

三个 reconciler 各管一个，遵循标准 Kubernetes 模式：watch 期望状态，和观测到的 Pod 做 diff，用幂等操作收敛。

它们之间不互相调用，只通过两个契约通信：

分配注解。 Pool reconciler 在 BatchSandbox 上写 sandbox.opensandbox.io/alloc-status（已分配的 Pod、poolRef、generation）和 alloc-release；endpoints 注解携带解析好的地址，供服务器读取。Pod 上带 sandbox.opensandbox.io/pool-name 和 pool-revision 标签。

任务派发。 batch reconciler 内部有一个 TaskScheduler，把任务分配给 Pod，并调用每个沙箱 Pod 内的 task-executor HTTP 服务。

用注解而不是新 API 做进程间通信，符合 Kubernetes 的一贯做法：可观测、可调试、可以用 kubectl 直接看。代价是注解没有 schema，改字段要小心兼容。

Pool 的容量模型

这是本章最值得细看的部分。Pool 有两级容量：

poolMin ─────────────── poolMax        总池：拥有的一切 Pod（含已分配）
        bufferMin ─── bufferMax        缓冲区：Running + Ready 且未分配的 Pod
  • 缓冲区是分配真正能拿走的东西，控制器持续把它收敛到 [bufferMin, bufferMax]：分配抽干缓冲区就扩容，释放后超过 bufferMax 就缩容。
  • 总池由 poolMin/poolMax 界定。还在启动的 Pod 计入总数，但永远不会被算作可用缓冲区。

第二句话是整个设计的关键：池子不承诺它交不出来的容量。如果只看总数，一个刚创建、还没 Ready 的 Pod 会被算作可用，分配请求就会拿到一个还不能用的沙箱。

扩容是节流的：每次 reconcile 最多创建或删除 maxUnavailable 个 Pod（默认 25%，绝对数或百分比）。文档的理由是避免「一波分配引发一场 Pod 雪崩」。这条限制和「快」看起来矛盾，其实不矛盾：缓冲区保证稳态快，节流保证突发时集群不被自己打垮。

分配与回收

分配是一次常数时间的认领：Pool reconciler 把 Pod 调度给等待中的 BatchSandbox，然后把分配结果写进注解。没有新的调度往返。

回收由 recycleStrategy 决定：

策略 行为 代价
Delete（默认） 换一个全新 Pod 每次分配都从模板的干净状态开始
Restart 原地重启容器 比换 Pod 便宜，进程状态被清
Noop 原样归还 最快，但文件系统和进程状态会泄漏到下一次分配

Noop 的存在很坦诚：它是给「沙箱内部自己负责清理」的场景留的口子，并且文档明说了泄漏风险。这里能看到一个成熟设计的特点——把危险的选项保留下来，但把代价写在文档第一行。

池化带来的三个 API 约束

因为池里的 Pod 在任何请求之前就存在了，生命周期 API 无法把请求级状态注入进去。文档因此列了三条硬约束：

  1. entrypoint/env 变成分配后下发的 task，而不是改写 Pod。所以在 Pod spec 里看到的是模板原本的 entrypoint，这是预期行为，不是 bug。
  2. volumes 和 networkPolicy 不能与 poolRef 同时使用，必须提前配在 Pool 模板里。
  3. 池 Pod 必须满足 task 契约（有 in-pod task-executor、bootstrap entrypoint、装好 execd），否则生命周期 API 用不了它们。

这三条是「预热」与「每请求定制」冲突后的落点，也是第 1 篇说的需求冲突在这里的具体形态。

容量耗尽：429 而不是排队

当没有可用的池槽位时，控制器会在等待的 BatchSandbox 上写入 PoolAllocationPending 条件（reason PoolCapacityExhausted），每 5 秒重查一次。服务器侧则等待一个有界窗口，窗口内没等到就返回可重试的 429。

这个设计有三个值得学习的细节：

  • 失败被编码成一个条件，而不是只写日志。运维可以 kubectl describe 看到原因。
  • 服务器不无限等。它把「池满」当成一种正常的、可重试的失败，而不是系统故障。
  • 窗口期内释放的槽位仍然可以满足这个请求——所以不是「立刻拒绝」，而是「有限等待后再拒绝」。

创建为什么会「同步成功」

生命周期 API 整体是异步的（返回 Pending），但 Kubernetes 后端有一个例外行为：使用 BatchSandbox 或 agent-sandbox provider 时，服务器会等工作负载进入 Running 或 Allocated 后才返回成功。

配置项在 [kubernetes]：

配置 默认 含义
sandbox_create_timeout_seconds 60 创建等待上限
pool_acquisition_timeout_seconds 30 池容量耗尽的累计等待上限
sandbox_create_poll_interval_seconds 1.0 无通知时的兜底轮询间隔

实现上用了已有 watch：工作负载变化会唤醒对应的等待请求，并直接评估事件自带的对象，不额外读一次 API。没有订阅能力的 provider 继续轮询。

文档特意说明了一点：这只保证工作负载 Running，不保证你的应用就绪。客户端仍然要用 execd 的 /ping 或自己的健康检查确认可用。

状态怎么读

BatchSandbox 的 status.phase 和 conditions 是两套视角：

  • phase 报运行时健康：Pending（还没有 Running+Ready 的 Pod）、Succeed（至少一个 Pod Running+Ready，这是稳态，不是任务完成）、Pausing/Paused/Resuming、Failed（终态运行时失败）。
  • conditions 解释原因：Ready、Progressing、Paused、PauseFailed、ResumeFailed、PodFailed、PoolAllocationPending。

文档给了两条使用纪律：只在条件 status: "True" 时计数；读更新后的 status 前先比较 status.observedGeneration 与 metadata.generation。第二条尤其重要——否则你会把上一代的状态当成本次操作的结果。

暂停与恢复：把 rootfs 变成镜像

Kubernetes 后端的暂停不是 docker pause。它的流程是：

pause
  → 创建内部 SandboxSnapshot
  → 在源节点上跑 commit Job，把容器 rootfs 提交成 OCI 镜像并推送 registry
  → 释放 Pod 与池槽位
  → 状态 Paused

resume
  → 复用同一个 BatchSandbox，把 template 改写成最新快照镜像
  → 重建运行时
  → 状态 Running

四个约束必须记住：

  • 只支持单副本（spec.replicas=1）。内部快照记录的是一个源 Pod 的容器镜像，无法表达每副本状态。
  • Succeed 才代表可恢复。对 rootfs-v1，只有在 commit Job 为每个容器都报告了镜像 digest 后才发布 Succeed；读不到结果（例如 commit Pod 被提前删除）会标 Failed 并给出 CommitResultUnavailable / CommitResultIncomplete，此时运行时 Pod 保留，沙箱报 PauseFailed，可以重试。
  • Pod 终止可以晚于 Paused。这个窗口里提交 resume，控制器会等旧 Pod 消失再建新的；带删除时间戳的 Pod 不再贡献新的失败条件。
  • 内存不保留（除非启用 QEMU-in-runc 模式）。rootfs 模式恢复的是文件系统，进程会重启。

还有一个容易踩的时间学问题：暂停请求被接受、或快照处于 Pending/Committing，都不构成持久性保证。只有镜像真的推到 registry 才算。文档还提到一条「尽力而为」的运维救急路径——image-committer 有时能从 containerd 直接读已停止的容器，但这不是支持的持久性契约。

性能数怎么读

文档给的对比很醒目：

场景 总耗时
agent-sandbox（并发 1 / 10 / 50） 76.4 s / 23.2 s / 33.9 s
BatchSandbox（启用池化） 0.92 s

同一个「交付 100 个沙箱」的任务，差了两个数量级。为什么？

  • agent-sandbox 走的是标准 Pod 调度链路，每次创建都要等调度、拉镜像、启动、就绪；
  • BatchSandbox 启用池化后，创建是认领已有 Pod，几乎没有调度开销。

这个对比不能被读成「agent-sandbox 慢」。它说明的是「预热 vs 不预热」的差异，而 agent-sandbox 是作为外部 provider 接进来的，它有自己的池化能力（SIG 的 Agent Sandbox 项目本身也提供池）。文档给的是 OpenSandbox 这条集成路径上的实测，读者要自己判断可比性。

本章要点

  • 三个 CRD：BatchSandbox、Pool、SandboxSnapshot；三个 reconciler 通过注解和 task 派发协作。
  • Pool 是两级容量：缓冲区（可分配）与总池（含启动中）。启动中的 Pod 不计入可用容量。
  • 分配是常数时间认领；回收有 Delete/Restart/Noop 三档，各有明确代价。
  • 池化带来三条 API 约束：entrypoint/env 走 task、卷与网络策略不能与 poolRef 同用、池 Pod 必须满足 task 契约。
  • 池满返回可重试的 429，并留下 PoolAllocationPending 条件。
  • 暂停 = 提交 rootfs 镜像 + 释放 Pod，单副本限制，Succeed 才算可恢复。
  • 100 个沙箱 0.92 s 是「池化 vs 非池化」的对比，不是两种项目的性能排名。

Fast Sandbox：模板、Fastlet 与 Firecracker

前三篇讲的两种后端都在「容器」这个单位上思考。Fast Sandbox 换了一个单位：模板。

在 Fast Sandbox 里，一个沙箱在创建请求到来之前就已经被决定了大半：运行时、镜像、entrypoint、环境变量、资源形状都固定在模板里；创建请求只表达意图——用哪个模板、谁在用、用多久。这一篇讲这个模型，以及它为什么需要一整套外部的控制面。

它在架构里的位置

Fast Sandbox 不是新的 runtime.type。Runtime.type = "kubernetes"，CompositeSandboxService 把带 templateId 的创建请求分给它，把 fsb- 前缀的既有沙箱操作也分给它。

控制协议是 gRPC（FastPath v2，端口 9090）。但 gRPC 只到 FastPath 为止：FastPath/Reconciler 到 Fastlet 的控制协议是 JSON over HTTP（/api/v2/fastlet/*）。持久化状态不在任何进程的内存里，而在 sandbox.fast.io 的 CR 里。

外部平台（FastPath、Fastlet、CRD）由 opensandbox-group/fast-sandbox 拥有，OpenSandbox 只提供适配层与 endpoint 集成。这条边界很重要：本书讨论的是适配与被观察的语义，不是那套平台内部的实现。

九个组件各自的职责

组件 职责 设计目标
FastPath gRPC 控制面，承担全部变更与实时操作 内存内放置决策，创建常数时间；可重启，因为持久状态在 CR 里
Reconcilers 把 CR 驱动成现实：建模板、跑池、放置沙箱、完成快照 观察即收敛，无 leader election
sandbox.fast.io CRD 每个沙箱的意图、放置、策略绑定、观测结果 意图能活过任何组件失败
Fastlet 预热 Pod，一个 Fastlet 里放多个沙箱 密度与隔离：网络槽位预置，egress 与 DNS 共享
runtime agent 每节点一个，经 unix socket 管 Firecracker VM 生命周期 节点自治：控制面委派，节点自检后才收活
DART 节点间 P2P 制品分发 摊薄源站：每个块全集群大约只从源站取一次
egress process 每 Fastlet 一个，服务 N 个沙箱的出向策略 无 per-sandbox sidecar 也能 fail-closed
模板构建器 OCI 镜像 → golden image（含 guest 接线与 execd） 负载在任何请求之前就固定
janitor 扫掉失败操作的孤儿资源 收敛负责补齐，janitor 负责清除

第三条与第七条是这个架构的支点：状态在 CR 里，负载在构建时固定。前者让所有组件可重启，后者让创建路径极短。

模板：两层，一个制品

模板存在于两个地方，这是刻意的：

  • 服务端持久化元数据（SQLite/PostgreSQL）是模板定义与租户归属的事实来源。模板是租户私有的，通过同一个服务器管理，用同一套认证与租户逻辑。
  • SandboxTemplate CR 驱动 fast-sandbox 侧的实际构建。服务器持久化定义并创建 CR，平台的 builder 异步把它变成 golden image。

构建产物不是简单的镜像复制，而是一次转换：普通 OCI 镜像 + OpenSandbox 的 guest 接线，编译成不可变的 golden image。

  • guest 接线被注入：init 路径（PID 1，携带就绪标记与心跳）与 execd 运行时文件总是来自模板，所以由它构建出的每个沙箱都「天然 execd-ready」。
  • 业务 entrypoint 与 env 被烘进去：空 entrypoint 默认成 keep-alive，env 字面注入（没有运行时间接层）。
  • 运行时形状被声明：模板指明 Firecracker 的 guest kernel 与参考机型，以及「什么算就绪」。
  • 输出是内容寻址的：构建把制品发布到 store，并在 CR status 里记录 manifest 引用与 digest。构建不可变、可验证，绝不原地修改。

于是创建请求里不能带 entrypoint、env、volumes、资源——它们属于模板。服务器适配层会直接拒绝这些字段（第 5 篇已提过）。

模板的第二个性质：更新会产生新 digest，而已运行的沙箱继续用当初被接纳的版本。新的创建才用新构建。这就是内容寻址 + 构建不可变带来的行为。

创建热路径

POST /v1/sandboxes {templateId, timeout, metadata, networkPolicy}
  → 服务器持久化/校验，向 FastPath 提交 intent（gRPC）
  → FastPath 在内存候选里排序：镜像缓存亲和 → 归一化负载 → 稳定哈希
  → 在选中的 Fastlet 上原子接纳：分配网络槽位、写 CR（意图 + 初始策略 + pool 引用）
  → runtime agent 恢复 vmstate.snap，或启动 VM
  → 沙箱 Running；客户端重新解析 endpoint

三个细节值得停一下：

网络槽位先于运行时存在。 netns、veth、masquerade 在任何创建请求之前就为沙箱预置好了，attachment 身份与策略绑定随接纳一起下发。所以沙箱永远不会「先能通网、后被策略覆盖」。

CR 先写、且写全。 意图、初始策略、pool 引用在运行时启动之前就持久化。被任何失败打断的接纳都能被 reconcile 补齐，不会漏掉半个沙箱。

entrypoint 作为 task 下发，而不是烘进 Pod。这让一个预热 Fastlet 能服务任意模板。

网络：签名路由与共享 egress

Fast Sandbox 的网络在入向和出向各有一个适配器，都在本仓库里。

入向由 ingress 的 FastSandboxProvider 承担：

  • 一条路由是签名的 f1. scope，绑定租户命名空间、沙箱 ID、端口，用 opensandbox-fsb-route-v1 方案签名，ingress 共享服务器的签名密钥环。
  • 客户端必须原样保留返回的路由与头——scope 就是凭据。
  • 服务器签发路由时不调用 FastPath、不等就绪：签名是本地操作，所以签发与沙箱状态解耦，endpoint 发现不构成存在性证明。
  • 请求到达时 ingress 才调 ResolveEndpoint。失败语义是契约的一部分：FailedPrecondition（含路由尚未发布）以 503 + Retry-After 出现，绝不能被报成「沙箱不存在」——ingress 不能泄漏「没就绪」与「不存在」的差别。
  • 通配 host 模式故意不支持：命名空间、沙箱 ID、MAC 塞不进一个 DNS label。
  • 两种访问模式：direct-fastlet-proxy（默认，ingress 直连 Fastlet Pod IP，低延迟）与 central-proxy（多一跳，不要求 Pod IP 可达）。

出向是这一篇最值得抄的设计。Fastlet Pod 里放着很多沙箱，per-sandbox sidecar 不适用，所以 egress 组件以 OPENSANDBOX_EGRESS_PROFILE=fast-sandbox 运行：每个 Fastlet Pod 一个 egress 进程，服务 N 个沙箱，每个沙箱是一个 subject。

subject 有自己的状态机：

absent ──SET_BINDING──► denying ──data-plane-ready──► active
   ▲                        │                            │
   └──────REMOVE_BINDING────┴────────────────────────────┘

从注册开始就是 denying，只有数据面确认就绪才 active。文档的措辞很准：策略可以迟到，绝不能提前放行。

策略怎么到 subject？作为数据，走 sandbox.fast.io CRD 的 revisioned actionBindings；只有凭据是带外的、只在内存里的。执行靠 nftables，按源 IP 分发：

  • 每个沙箱有一个预置的网络槽位，attachment.ip 就是分发键，共享 DNS 代理按 ip saddr 选 subject。
  • forward 路径用 meta mark 0x2 标记允许的目标，master 链丢弃未标记流量。这条路径故意不发显式 accept：在 bridge-nf-call-iptables=1 的拓扑下，accept 裁决会把帧送回二层而丢失。
  • DNS 学到的 IP 有界租约，活跃 TCP 连接有刷新循环续租；UDP/QUIC 只靠 DNS TTL。
  • DoT（853）总是丢，DoH-over-443 可选阻断。

这套设计的价值不在 nftables 语法，而在「共享基础设施 + 每 subject 隔离」这个折中：省掉了 N 个 sidecar 的资源，代价是策略执行路径变复杂，必须用 UID/IP/端口三重作用域把管理面与数据面隔开。

检查点、暂停、快照

Fast Sandbox 的暂停把运行时状态检查点写进同一个内容寻址 store，其中 golden image 也放在那里。一个检查点包含：

部分 内容
rootfs 沙箱可写根文件系统
vmstate microVM 的设备与 vCPU 状态
memory guest 内存（捕获期间经节点 /dev/shm 暂存）
SHA256SUMS 整个集合的 digest 清单

Sandbox 记录的 status.runtime.checkpoint 存 checkpointID（由 sandbox UID、请求暂停的 spec generation、pauseAttempt 重试纪元派生）、manifestRef（s3:// URI）、digest 与大小。检查点先写 digest 后写内容：只有制品集完整落到 store，暂停才被报告为完成。没有记录检查点的 Paused 沙箱无法恢复，只能重置。

暂停的第 3 步是释放 Fastlet 容量。所以一个 paused 沙箱的算力足迹是零。

恢复的关键性质是可移植：在任意被接纳的 Fastlet 上恢复，不一定是原宿主机。这就是为什么路由必须重新解析——恢复会推进 route generation，旧路由不会跟着沙箱跑到新宿主机。

快照是同一套机制的公开形态：POST /sandboxes/{id}/snapshots 只接受 Running 源，创建确定性命名的 SandboxSnapshot 记录 + sandboxRef.uid 围栏，然后持久化 CREATING 行。文档的说法是「运行时意图永远在一行可读记录后面，在每个副本上」。之后由平台推进 Pending → Creating → Publishing → Succeeded/Failed。恢复时 POST /sandboxes {"snapshotId": ...} 从 READY 快照创建，沙箱 ID 是新的——快照是起点，不是延续。

删除快照记录不删除已推送的制品。存储保留是运维策略，被有意留在沙箱生命周期之外（第 17 篇会把它和容量规划放在一起）。

存储：一个 store，私有缓存，P2P 分发

Fast Sandbox 把存储压缩成一种形状：沙箱运行或恢复所需的全部东西，都是单一 S3 兼容 store 里的内容寻址制品。

节点保留私有状态根：XFS reflink 支撑的本地缓存，节点之间不共享。这是有意的——快速启动来自本地制品，跨节点共享状态会把每个节点变成别人故障域的一部分。

私有缓存的代价是重复下载，DART 消除它：每节点一个投递守护进程，通过 headless Service 名册互相发现，4 MiB 块级取数走 cache → peer → origin，每个块全集群大约只从源站取一次。每节点的块来源计数（cache/peer/origin）让投递路径可观测。

文档明确列了「故意不存」的三样东西，这段很值得读：

  • egress 凭据只在 egress 进程内存里，绝不写 Secret 卷或磁盘；
  • 沙箱的运行时写入在沙箱自己的切片里，只有显式检查点或快照才捕获——「沙箱的存储是生命周期的一个动作，不是后台同步」；
  • 路由与策略状态在 CRD 里，store 只放字节。

Firecracker 与节点自检

模板构建 golden image 时就是为 Firecracker 准备的，每个沙箱是 Fastlet Pod 网络命名空间里的一台真 KVM 虚拟机。

宿主要求（在 chart 与环境工具里实际检查的）：

  • 宿主内核 ≥ 5.10；
  • /dev/kvm 存在并透传进节点容器（含 /sys 下的 KVM 设备节点），嵌套虚拟化可用即可；/dev/net/tun 用于每沙箱 netns 的 TAP；vhost-vsock 故意不挂；
  • /dev/shm 大于容器默认值（快照内存暂存在这里）；
  • cgroup v2（v1 宿主直接拒绝）；
  • 提高 fs.inotify.max_user_instances；
  • 节点状态根在 XFS + reflink 上：每沙箱 rootfs 是 CoW reflink，setup 会显式探测 reflink，探测失败就拒绝而不是降级；
  • 余量：默认要求 10 GiB 空闲磁盘与 2 GiB 空闲内存。

节点就绪是自助的：firecracker-runtime DaemonSet 在每个候选节点跑检查、装 Firecracker 资产（默认 v1.16.1），通过后才给节点打标签（sandbox.fast.io/kvm=true 等）并设 FirecrackerReady 条件。池只把 Fastlet 放到打过标签的节点上，运维不用手工打标签。

网络模型里有两个踩过的坑，文档写得很具体：

  • 每 VM 独立网关地址。 共用一个网关在 arp_ignore=1 下会坏：第二台 VM 的 ARP 没人应答，流量出不了 guest。所以每 VM 一对 veth 与独立网关 IP，egress 按 attachment 自动分发。
  • guest 流量绕过容器 netfilter。 跨 VM netns 的流量从 Pod 视角是二层桥流量，所以权威执行层是 pod-netns 的 forward 链，不是容器 OUTPUT 路径。

生命周期顺序是固定的：建 VM netns → SET_BINDING（deny-first）→ data-plane-ready → 沙箱流量在自身策略下流动。

性能数怎么读

文档给的 ACK 两节点实测（2026-10-08，Firecracker 1.16.1，模板制品已缓存）：

指标 成功率 p50 p90 p99
SDK 创建，串行基线（100 次） 100/100 64.0 ms 93.8 ms 108.3 ms
SDK 创建，并发 10 100/100 102.7 ms 120.1 ms 125.4 ms
SDK 创建，并发 20 51/100 136.7 ms 163.0 ms 197.0 ms

读这张表要带三个前提：

  1. SDK 就绪包含整条链：Python SDK、生命周期服务器、FastPath、ingress gateway、guest /ping 200。运行时创建更早结束（同窗口的 runtime create p50 是 33–50 ms）。
  2. 并发 20 那一行只统计成功的尝试。48 次 SandboxRateLimitException（HTTP 429 / Fastlet CapacityRejected）和 1 次就绪超时被排除在外。文档自己写明：这次运行不能证明 20 路并发接纳可靠，也不能给出可持续的 RPS。
  3. 同节点恢复仍然慢。运行时恢复是几十毫秒（resume runtime creation 中位 35.49 ms），但 SDK 恢复中位 62.66 秒。文档明确指出：大部分时间花在 endpoint/guest 可用性与客户端等待上，无法用复制 2 GiB rootfs 或跨节点取检查点解释；这个差距尚未定位。

这三条一起说明了一件事：预热能把「运行时创建」压到几十毫秒，但不能自动把「端到端就绪」压到同量级。第 18 篇会把这条当作「性能优化要优化在哪一层」的例子。

高可用：单控制面是设计立场

Fast Sandbox 的控制器（reconciler + FastPath）单副本、无 leader election。文档把这个决定写成了立场而不是遗漏：

  • 变更快，正是因为 FastPath 可以把放置与候选状态放在内存里；复制控制面就得对这份状态做共识。
  • 没有持久状态依赖那份内存。崩掉的只是进行中的 reconcile，CR 会重放。
  • 因此沙箱的可用性与控制面的可用性解耦：控制面重启时，运行中的沙箱继续跑，流量继续流。

恢复统一用「提交意图 + 观察持久记录收敛」，不用 lease：

失败 影响 恢复
控制面重启 短暂失去变更能力，运行中沙箱不受影响 CR 驱动重放意图
Fastlet Pod 丢失 该 Fastlet 上的沙箱中断 按 failurePolicy 在 recoveryTimeoutSeconds（默认 60 秒）后处理，默认人工
服务器重启 沙箱无影响，未完成的操作从持久记录继续 同一套观察-收敛
制品 store 故障 新启动降级为直接拉取，运行中沙箱不受影响 store 恢复后 DART 继续服务

本章要点

  • Fast Sandbox 是 Kubernetes 模式下的组合分支，通过 templateId 与 fsb- 前缀路由；控制协议是 gRPC 到 FastPath，控制面之外用 JSON over HTTP。
  • 模板两层：数据库里是定义与租户归属的事实来源，SandboxTemplate CR 驱动构建；构建产物是含 execd 的内容寻址 golden image。
  • 创建走「内存放置 + 原子接纳」，网络槽位与 CR 都先于运行时存在。
  • 入向是签名的 f1. scope，签发与就绪解耦；出向是每 Fastlet 一个共享 egress，按 subject 分治、按源 IP 分发，fail-closed。
  • 暂停写 rootfs+vmstate+memory 检查点并释放 Fastlet；恢复可能换宿主机，所以必须重新解析 endpoint。
  • 存储是一个内容寻址 store + 节点私有 reflink 缓存 + DART P2P。
  • 控制面单副本是立场；沙箱可用性与控制面可用性解耦。
  • 64 ms 的创建与 62 秒的恢复并存，因为两者度量的完成边界不同。

数据平面：execd 的命令、文件与流式语义

前面八篇都在沙箱外面。这一篇进到里面。

components/execd/ 是一个 Go 写的守护进程，用 Gin 做 HTTP，默认监听 44772。它是 OpenSandbox 的沙箱内执行 API 参考实现：命令、文件、目录、代码上下文、PTY、指标、隔离会话。它同时还能当沙箱的 init 进程。

它会出现在三种部署形态里：Docker 里由服务器暂存二进制；Kubernetes 里由 init 容器把 execd 与 bootstrap.sh 从 execd_image 拷进 emptyDir，再挂给主容器；Fast Sandbox 里烘在 guest 镜像里。

一个 API，一句令牌

所有端点都在同一个 API 下。开启访问令牌后，每个端点都要求 X-EXECD-ACCESS-TOKEN，只有存活与就绪探针永远开放。

区域 端点 说明
健康 /ping、/ready 无需令牌
命令 /command、状态、日志 前台流式或后台轮询
Shell 会话 /session、/session/{id}/run 跨调用保持状态
代码 /code、/code/contexts Jupyter 内核上下文
终端 /pty WebSocket 接入
文件 /files/*、/directories 完整文件系统面
隔离会话 /v1/isolated/* 私有命名空间的 shell
指标 /metrics、/metrics/watch 快照与实时流
反向代理 /proxy/{port} 一个宿主端口触达所有端口

这个令牌的语义要看清：它是沙箱级的凭据，不是「终端票」。文档明确说它应该通过授权的 endpoint 解析流程拿到，不要放进 URL 或浏览器持久存储，生产环境要用 WSS——因为 base64url 不是加密。

命令：两种形式、两种模式、三条语义

命令有两种提交形式：

  • shell 语法：管道、重定向、环境展开，就是你在提示符下会敲的东西；
  • 直接 argv：程序 + 字面参数，不经 shell 解析。当命令的一部分来自不可信输入时更安全，并且能精确保留空串和特殊字符。

两种模式：

  • 前台：命令运行期间以 SSE 实时推流，返回后流关闭；
  • 后台：立即返回，之后轮询状态、增量取日志。已完成的后台输出保留 24 小时，运行中的命令永不被清理。

三条语义是第 3 篇提到的契约条款，这里说清它们为什么必须存在。

行尾保留。 前台 stdout/stderr 事件的文本保留命令原始的行尾（\n、\r、\r\n）。按流拼接事件文本即可还原输出，最后一个事件可能是不完整的一段。这一条看似琐碎，但它决定了客户端能否实现「逐行渲染进度条」这类需求——如果 execd 悄悄把 \r 换成 \n，进度条就变成几千行日志。

成功也有退出码。 前台 POST /command 以 execution_complete 携带 exit_code: 0 结束。这个字段是可选的：后台启动确认里没有，代码执行事件里也没有，缺失不代表成功。非零退出保留在 error 事件的 error.exit_code 上。

流提前结束不构成成功。 在终止事件之前断流，只能当作不确定。这一条是对「客户端乐观推断」的明确拒绝。

文档还记录了一次真实兼容事故，值得完整转述，因为它示范了「协议演进如何变成客户端崩溃」：sandbox-api 1.0.18 之前的 SDK 不认识 exit_code 字段。当消费者的 classpath 解析到不兼容的 kotlinx-serialization 运行时时，解码未知字段会以 AbstractMethodError 崩溃——命令在沙箱里跑完了，客户端调用永不返回，也不打日志。

上游的处置分两层：短期给 EXECD_SSE_LEGACY_COMPAT=true，让 execd 在两个事件里都省掉该字段（成功的命令不损失信息，因为值恒为 0，新 SDK 会推断）；长期是让 SDK 遮蔽自己的序列化运行时（sandbox-api 1.0.18 起），从而消除「每加一个字段就多一个风险」的结构问题。这段的价值在于它承认了「加一个可选字段」在强类型客户端生态里不是安全的操作。

Bash 会话：合并流与 16 MiB 的行

/session 提供一个跨调用有状态的 shell。两次 run 之间共享 shell 状态（export X=1 对下一次可见），这是它和命令执行的根本区别。

实现上有几个具体决定：

  • 合并流。会话运行只推一路 stdout 事件，会话的 stderr 被合进去。因为 shell 会话的语义是「一个终端」，分离两路反而失真。
  • 空行保留。只有行尾的空行也是一个事件。
  • 超长行切分。超过 16 MiB 的行被拆成多个事件，只有最后一个带行尾。
  • shell 回退。镜像有 bash 就用 bash，最小镜像回退到 POSIX sh——此时命令必须是 sh 兼容的。Windows 沙箱也支持（环境变量名大小写不敏感，批处理文件需要 shell 语法）。

代码上下文是 execd 管理的持久 Jupyter 内核。你在一个上下文里执行代码，收到流式结果（标准输出、执行结果、错误），多次调用共享状态——和 notebook 一样。

官方 code-interpreter 镜像（在 opensandbox-group/sandbox-images 仓库）带 Python、Java、Node.js、Go 运行时和对应内核。语言版本由镜像控制，经 PYTHON_VERSION 这类环境变量选择。

这里有一个架构上的分层：Code Interpreter SDK 是可选的高层客户端；底层的执行 API 通过普通沙箱 SDK 或直接调 execd 也能用。第 3 篇提到「shell-only 镜像不支持 notebook 式代码执行」——因为代码执行的实现依赖 Jupyter 与已装内核，不是 execd 凭空提供的。

PTY：一个持有者，若干观看者

终端会话是真的 PTY，走 WebSocket，不是「包装过的命令」。所以编辑器、REPL、Agent CLI 这类交互程序能正常工作。

共享模型是刻意设计的：恰好一个 holder 拥有键盘，任意多个 viewer 可以观看。viewer 先回放已打印内容，再跟实时输出。用途很具体：监督、调试助手、让第二个人看着 Agent 干活但不给它输入。

浏览器有一个现实问题：WebSocket 握手不能带任意头。所以 GET /pty/{sessionId}/ws 允许用子协议传凭据：offer opensandbox-pty 应用子协议 + 一个凭据子协议，后缀是 execd 令牌的无填充 base64url。execd 验证后移除凭据项，只协商 opensandbox-pty。

规则写得很细，说明这块踩过坑：

  • 显式 X-EXECD-ACCESS-TOKEN 头优先，即使它是空或非法，绝不回退到子协议；
  • 重复凭据、编码错误、没有应用子协议只有凭据，都返回 401；
  • 既有走头的客户端不需要提供子协议；
  • 其他 HTTP API（含 PTY 创建与删除）仍然要求头。

文件：先暂存再改名

文件 API 覆盖整棵文件系统树：流式上传下载、列举、搜索、改权限、替换内容、移动、删除。

上传有一个值得学的实现细节：先写到目标旁边的暂存文件，再 rename 就位。这样一次中途失败的复制不会截断它正在替换的旧文件。前提是对所在目录有写权限；当只有目标文件可写（例如 0555 目录里的 0666 文件）时，execd 回退到原地写入——上传仍会成功，但部分失败可能截断旧内容。

几个附带承诺：

  • 替换保留目标的 mode，包括 setuid/setgid/sticky 位，并在平台允许时保留 owner/group；
  • 目标已存在时，暂存文件私有创建，且从目录列举与搜索结果里隐藏；
  • 隔离会话的上传路由（/v1/isolated/session/:sessionId/files/upload）不做暂存，保持原地行为。

以指定身份执行文件操作是一个更强的特性：Linux 上，可信后端可以在路径前加 /v1/filesystem/{uid}/{gid}，让操作以该身份执行。每个请求跑在独立 worker 进程里，用选定的凭据；补充组来自选定用户的系统账户（未知数字 UID 没有补充组）；worker 不继承 execd 的补充组，也不继承 execd 的环境。相对路径从 / 解析，~ 用选定账户的家目录（未知 UID 用 /）。

但要看清边界，文档自己写了两条：

  1. 它不提供独立的 mount namespace，不是租户隔离边界；
  2. 上传的 owner/group/mode 是目标元数据，不能给 worker 提升权限。

这个特性解决的是「同一个沙箱里多个会话共用一个工作区」的权限问题：给每个会话分配独立用户与目录，写权限留给属主。文档提醒删除与重命名权限取决于父目录，所以只读文件权限不够。

隔离会话：bubblewrap 的每执行命名空间

隔离会话在一个 per-execution 的 bubblewrap 命名空间里跑 shell，每次新建：私有挂载视图与身份。显式 bind mount 把宿主路径带进来（只读或读写），写入被限制在允许列表内，并且校验的是完全解析后的路径，所以符号链接不能把 bind 重定向到列表之外。会话创建会报告当前环境支持什么，调用方据此调整而不是猜。

成本数字很清楚：创建一个会话约 100 ms（execd 会短暂等待以检测立即退出的子进程），之后每次 run 复用同一个 bash，开销可忽略。所以它适合「一次 sandbox、多次隔离任务」的场景（RL rollout、批量判题、多工具 Agent），不适合跨语言内核（用 /code）、交互式 REPL（用 /session）、或硬信任边界（用 gVisor/Kata）。

契约里的 diff/commit 没实现，返回 503，/v1/isolated/capabilities 如实报告 diff_supported: false、commit_supported: false。这是第 3 篇「契约覆盖 ≠ 实现能力」的实例。

分层防护与「它到底生效了吗」

execd 对沙箱里跑的一切做了纵深防御，四层：

  1. 沙箱边界：资源限制、身份、隔离运行时（runc/gVisor/Kata/Firecracker），在创建时选定；
  2. 加固地板：运维开启后，每个用户进程经原生 launcher 启动，drop capabilities、设 no_new_privs、装 syscall 拒绝列表、用 Landlock 限制文件系统写；
  3. 隔离会话：上面的 per-execution 命名空间；
  4. 可选 eBPF 审计：记录 exec、connect、权限变更，作用域是沙箱自己的 cgroup，作为单独的 execd-ebpf 构建变体发布，不在默认镜像里。

第四层之外的每一层都会报告自己的状态：active、degraded 或 unsupported。这条设计比「我们有四层防护」重要得多——客户端能验证实际生效的是哪几层，而不是假设。

同时有一条必须说清的边界：execd 的生命周期钩子是平台配置的可信代码，在沙箱内运行。文档原话是「它们是便利，不是安全控制」。

当 init 与「每次分配一个新身份」

execd 可以当沙箱的 init 进程：回收孤儿进程、把信号转发给 entrypoint、把自己的退出码传给运行时，于是 Terminated/Failed 反映的是你的进程真的做了什么，长会话也不会积累僵尸进程。

更微妙的是预热复用时的身份问题。沙箱可以在池里预热并被不同分配复用。execd 让这件事安全：平台在分配时下发一次 per-allocation 绑定（沙箱 ID、环境、访问令牌、生命周期钩子），execd 在 API 开放之前原子地应用它。在等待绑定期间（以及启动完成之前），所有业务端点返回 503，只有 /ping 与 /ready 响应。

这样环境变量、令牌、遥测归属就不会从上一个沙箱泄漏到下一个。这是「预热」这个优化在数据面必须付的代价，也是第 7 篇「池化带来 API 约束」的另一半。

指标与代理

execd 暴露本地 CPU/内存指标：快照（/metrics）与实时流（/metrics/watch）。平台配置了 OTLP 端点时，还导出 OpenTelemetry 指标，并归属到沙箱 ID 与 allocation。

内置反向代理 /proxy/{port} 是第 6 篇的主角：一个宿主端口触达所有容器端口。它还转发 Upgrade、Connection 等头，所以 HTTP、SSE、WebSocket 共用同一映射。

本章要点

  • execd 是沙箱内执行 API 的参考实现，默认 44772，一个沙箱级令牌保护所有端点（探针除外）。
  • 命令支持 shell 语法与直接 argv；前台 SSE、后台轮询；行尾保留、成功带 exit_code、断流不等于成功。
  • 会话合并 stderr、保留空行、超 16 MiB 行切分、bash→sh 回退。
  • PTY 是一持有者多观看者，浏览器可用子协议传 base64url 令牌；显式头优先且为空也不回退。
  • 文件上传先暂存再改名；身份前缀 /v1/filesystem/{uid}/{gid} 提供执行身份，但不是租户边界。
  • 隔离会话是 per-execution bubblewrap，约 100 ms 创建，diff/commit 未实现。
  • 防护分层且自报状态；生命周期钩子是可信代码，不是安全控制。
  • 预热复用靠 per-allocation 绑定保证环境与令牌不泄漏，未绑定前业务端点 503。

入向网络：endpoint 解析、ingress 与 secure access

客户端要访问沙箱里的服务，第一件事是知道地址。这件事在单机上很简单（localhost:40001/proxy/8080），在集群里就很麻烦：Pod IP 会变、Pod 会重建、网关要按租户鉴权、还得支持 WebSocket。

OpenSandbox 的做法是把「怎么访问」变成一个契约端点，然后用三种实现去填它。这一篇讲这三种实现、路由细节，以及一个容易被忽略的副作用——访问会延长沙箱寿命。

三种形态，一个契约

GET /sandboxes/{id}/endpoints/{port} 的返回永远是「能用的地址 + 必须带的头」，但形态有三类：

形态 何时使用 地址长相
直连 Docker 宿主映射、Pod IP 可达 host:40xxx/proxy/8080 或 10.0.0.12:8080
网关 Kubernetes + ingress 部署 gateway.example.com + 路由头
控制面代理 两者都不通 .../sandboxes/{id}/proxy/{port}

文档把第三类定性为兼容退路，不是快路径。这个定性很重要：它意味着代理层不需要为吞吐做极致优化，但必须正确——因为它是「其他路都走不通时」的最后一条路。

ingress 的两种路由模式

ingress 是一台面向所有沙箱的反向代理，没有 per-sandbox 配置。它 watch 工作负载已经发布的状态——endpoint 注解、Service FQDN、或 FastPath 控制面——然后在实时缓存里解析每个请求。

路由是一个「沙箱 ID + 端口」的组合，有两种发现方式：

  • 头模式（默认）：OpenSandbox-Ingress-To: <sandbox-id>-<port>，或者把同样的信息编码进 host label（my-sandbox-8080.example.com）。
  • URI 模式：路径前两段是这对信息——/<sandbox-id>/<port>/<path>——给不能设置头的客户端用。

三种后端的数据来源不同：BatchSandbox 从 sandbox.opensandbox.io/endpoints 注解读；agent-sandbox 读 status.serviceFQDN；Fast Sandbox 路由则问 FastPath 解析。

转发前的处理是标准反向代理动作，但都有具体清单：剥掉路由头、加 X-Forwarded-*、过滤逐跳头、精确保留路径与查询串。

最后一条比看起来重要。ingress 一旦「顺手」规范化路径（比如合并 //、解码 %2F），就会改变后端看到的语义，某些 Web 框架的路由匹配会因此不同。

错误语义：三种失败必须分得开

状态 含义
404 没有这个沙箱（或已不存在）
503 沙箱存在但没就绪，还没有可达的 endpoint
502 基础设施级失败（集群 API 错误等）

这三者的区分决定了客户端能否正确反应：404 该放弃，503 该重试，502 该告警。

第二条还有一条额外的纪律：沙箱被访问之后，响应原样透传，包括重定向与错误。ingress 自己从不跟随重定向——这样一条过期的 Location 永远不可能把凭据泄漏给无关端点。

Fast Sandbox 侧的等价规则更严格：FailedPrecondition（含路由尚未发布）必须以 503 + Retry-After 出现，绝不能被报成「不存在」，因为 ingress 不该泄漏「没就绪」与「不存在」的差别（第 8 篇讲过）。

WebSocket 是一等公民

很多同类代理把 WebSocket 当成「HTTP 的 upgrade 补丁」。OpenSandbox 把它当主路径处理，规则写得很细：

  • 升级遵循 RFC 6455 over HTTP/1.1，后端握手预算 45 秒；
  • 客户端选择的子协议与后端 Set-Cookie 头都要穿过握手；
  • 应用关闭码原样透传——策略违规（1008）或应用自定义码（4001+）不会被改写成 1000；
  • 单条消息最多 64 MiB，双向，按终端与 Jupyter 的流量规模设计；
  • Connection 头 token 大小写不敏感匹配，双向流不缓冲对端。

第二条与第三条说明了一个态度：代理层不做「善意改写」。关闭码被改写是最典型的坑——客户端会以为连接正常关闭，于是不重连。

在 ingress 前面放 TLS 代理时会发生什么

ingress 自己只说明文 HTTP/1.1，不做 TLS 终结。所以生产部署要在它前面放一个 L7 代理。但这里有一个技术约束：

WebSocket over HTTP/2（RFC 8441）不被接受，而 RFC 7540 又禁止在普通 h2 请求上带 Upgrade 头。所以前面的代理必须把 WebSocket 升级当作经典 HTTP/1.1 投递。

文档给了三档方案，按优先级：

  1. 把 h2 从面向浏览器的 ALPN 列表里去掉（最可移植，已验证）；
  2. 如果代理支持「对 WebSocket 回退 HTTP/1.1，其余保持 h2」，用它；
  3. RFC 8441 → RFC 6455 翻译（依赖具体代理，必须用真浏览器验证）。

底线更简单：永远不要把 HTTP/2 转发给 ingress 本身，因为升级永远到不了 WebSocket handler。

健康检查与被刻意区分开的「网络就绪」

ingress 有两个端点，语义不同：

  • /status.ok — 存活：进程在跑、在服务。
  • /status.ok/network-readiness — 一个影子信号：对最近窗口内 ingress 打开的 TCP 连接做分类（success、timeout、unreachable、refused 等），当 timeout 与 unreachable 在足够多不同目标上占主导时报 DEGRADED。

第二个端点永远返回 200，body 是 OK 或 DEGRADED，并且从不影响流量。文档的说法是「给运维看的决策输入，不是负载均衡钩子」。它的指标里刻意没有目标地址和沙箱 ID。

这个设计值得抄：把「我能不能服务」与「网络看起来健康吗」拆成两个信号，前者用于摘流量，后者只用于告警。混在一起时，一次跨节点网络抖动会导致大规模错误摘除。

secure access：endpoint 的头就是凭据

secureAccess 目前只支持 Kubernetes + ingress gateway 模式。开启后，服务器为 endpoint 预置凭据，并把必需的头随 endpoint 一起返回。配置了网关签名密钥时，还支持签名的路由令牌。

这里有个安全约束值得单独强调：endpoint 响应里的头是凭据。文档在 execd 的 PTY 章节也重复了一次（沙箱级令牌，不要放进 URL 或持久存储）。这类材料一旦被缓存到共享位置，等于把沙箱的访问权发出去了。

api/proxy.py 里有一条相关规则：当 endpoint 被改写成服务器代理 URL 时，服务器只移除 ingress 路由头 OpenSandbox-Ingress-To，保留其他必需的头。少移一个会泄漏路由信息，多移一个会让后端认证失败。

访问会延长寿命：renew-intent

这是一个容易被忽略的联动。开启后，ingress 在每个被代理的请求解析出沙箱之后发布一次 renew-intent 事件；生命周期服务器据此延长那些在创建时选择了续期的沙箱。

四个性质定义了这个机制：

  • 按沙箱节流，且尽力而为：空闲沙箱照样过期，繁忙沙箱无需客户端改动就能续命。
  • 单请求可以退出：OpenSandbox-Access-Renew: skip，只认精确值 skip，未知值忽略（向前兼容）。典型用途是健康探针不要延长沙箱寿命。
  • 两条代理路径都遵守：ingress 网关和服务器 /sandboxes/{id}/proxy/{port} 都实现，所以行为不取决于流量走哪条路。
  • 头在转发上游前被剥掉，和后端应用看到的路由头一样。

WebSocket 升级会在握手请求上携带该头，但长连接不会产生每请求的续期意图——这条边界在文档里写明了，因为「长连接算不算活跃」没有唯一答案，明说比猜好。

同一套机制还有一个近亲：OSEP-0024 的空闲暂停。它增加了 OpenSandbox-Skip-Activity: skip 哨兵，用于让观测探针不重置它自己测量的时钟。文档还补了一句很有意思的分析：伪造这个头只会伤到自己——自己的沙箱会显得更空闲、更可能在使用中被暂停，而下一个普通请求会把它唤醒。

本章要点

  • endpoint 有三种形态：直连、网关、控制面代理；代理是兼容退路不是快路径。
  • ingress 无 per-sandbox 配置，靠 watch 工作负载已有状态；头模式与 URI 模式并存。
  • 错误语义三分类（404/503/502），到达后响应原样透传，绝不跟随重定向。
  • WebSocket 是一等路径：45 秒握手预算、64 MiB 消息、关闭码不改写、不缓冲。
  • ingress 不做 TLS 终结；前置代理必须用 HTTP/1.1 承载 WebSocket 升级。
  • /status.ok/network-readiness 是影子信号，永不 gate 流量。
  • secureAccess 的头就是凭据；代理只移除路由头，保留其余。
  • renew-intent 按沙箱节流、尽力而为，OpenSandbox-Access-Renew: skip 可单请求退出，两条路径行为一致。

出向网络：DNS 与 nftables 的两层执行

入向要回答「怎么找到沙箱」，出向要回答一个更难的问题：怎么让一段模型生成的代码只访问它该访问的地方，且在它尝试绕过时依然有效。

这类需求容易写成一句「加个白名单」。真正动手时会发现三个问题：白名单按域名写，但实际连接按 IP 走；只做 DNS 过滤时，一次预先解析就能绕过；做包级过滤时，又必须知道域名解析出的 IP 集合，而这集合会变。

这一篇讲 OpenSandbox 的 egress 组件怎么把这三个问题分层解决。

形态：共用网络命名空间的 sidecar

egress 以 sidecar 形式与沙箱共享网络命名空间，所以每个出向包都经过它，应用无需任何配置，也无法从内部绕过。策略在创建时声明（networkPolicy）或由平台注入，之后持续执行。

部署 形态
Docker 独立 sidecar 容器；沙箱加入 sidecar 的网络命名空间
Kubernetes（容器） sidecar 追加到沙箱 Pod，持有 Pod 里唯一的 NET_ADMIN
池化沙箱 预热 Pod 无法按请求加 sidecar——控制必须写进 Pool 模板（networkPolicy + poolRef 会被拒绝）

第三行是第 7 篇那条约束的另一面；第四行是第 8 篇讲过的共享进程模型。

「只有 sidecar 有 NET_ADMIN」这个细节值得单独提：它意味着沙箱主容器没有能力改网络规则。执行位置在数据路径上，权限在数据路径之外——这是这套设计能挡住「从内部关掉防火墙」的根本原因。

Layer 1：DNS

所有 53 端口的流量被重定向到 sidecar 的 DNS 代理。行为只有两种：

  • 被拒绝的域名返回 NXDOMAIN；
  • 允许的域名正常解析到真实上游，并且解析出的地址被记录下来。

第二条是两层之间的接口：DNS 层不只是过滤器，还是「域名 → 地址」的发现机制。

Layer 2：网络（dns+nft 模式）

nftables 丢弃一切未被明确允许的流量。允许的流量靠两条路径通过：

  • 静态规则：IP 或 CIDR 直接允许；
  • DNS 学到的地址集：一个被解析出的 IP 获得有界租约（活跃 TCP 连接有一段宽限期），所以「允许」永远不会悄悄变成「永远允许」。

文档对 UDP/QUIC 说得很直白：它们只能依赖 DNS 租约时长，没有连接层面的续租。

这两层是两种成本：

只做 DNS 过滤 dns+nft
成本 低，通用 高，需要 netfilter 能力
挡住什么 按名字访问 按名字 + 按包，默认拒绝
挡不住什么 预解析 IP、直连 IP 已建立连接直到租约到期

优先级：平台永远压过租户

规则求值的顺序是固定的：

平台 deny.always  →  平台 allow.always  →  用户策略（第一条命中生效）

平台覆盖规则来自 sidecar 镜像里的文件（/var/egress/rules/deny.always、allow.always），每分钟热重载一次。重载有一条前提：只有 nftables 接受对应静态策略后才发布；解析或应用失败时保留上一份已接受的内存规则，并继续有资格重试。

这个顺序解决了一个治理问题：租户策略不能打开平台明令禁止的目标。文档的措辞是「平台的 deny 永远赢过你的 allow」。

还有第三层平台控制：reachable.ports.cap。它是一份 TCP 端口白名单（一行一个端口或 lo-hi 区间），sidecar 取补集，作为一条 always-deny 规则排在所有用户规则之前。所以无论沙箱的 defaultAction 或 allow 规则怎么写，只有白名单里的端口能通。文件缺失或为空表示没有地板。

端口范围规则与它的四条限制

一条规则的 target 可以省略而只给 ports，于是可以「按 TCP 目的端口」作用域化——{"action": "deny", "ports": [25]} 就是禁止出向 SMTP，不管目的地。target 与 ports 也可以组合，把一条 IP/CIDR 规则限定到特定端口。

限制写得很具体，说明这些是刻意划的线：

  • 只支持 TCP，没有 UDP；
  • 每条规则最多 256 个端口；
  • 域名目标不能与 ports 组合——域名规则在 DNS 层求值，那一层没有端口维度，校验时直接拒绝；
  • DELETE /policy 按 target 删除规则，而纯端口规则没有 target，需要用显式的空串 "" 来删。

还有一条与 DNS 层有关的语义陷阱：无 target 的 allow 规则，DNS 代理是看不见的。在 defaultAction: deny 下，主机名解析仍然返回 NXDOMAIN，所以这类规则只服务「直接拨 IP」的客户端。要按名字访问，就得写显式的域名 allow 规则（而域名规则不能带端口）。

Fast Sandbox profile 目前拒绝 ports（返回 400），直到它的执行路径支持为止。这是「能力差异显式声明」的又一个例子。

透明 TLS 拦截：能看、能控、能认证

前两层决定「连接能不能发生」。第三层（L7）决定「通过连接的内容能不能被看见与控制」：启用后，出向 HTTP/HTTPS 被重定向进 sidecar 内的 mitmproxy 监听器，它从连接状态恢复真实目的地，并代表沙箱终结 TLS。

文档对它的成熟度描述很精确：机制可用，配置面仍是实验性的。拦截、凭据注入、CA 投递都已完成并在生产环境使用；但额外端口与诊断开关可能在发布之间变化。

三个设计决定值得记：

信任是「投递」的，不是「关掉校验」。 sidecar 导出自己的 CA，沙箱 bootstrap 尽力把它装进系统、NSS、JDK 的信任库。客户端保持证书校验（curl 不带 -k）。Chromium 系镜像应该带原生 certutil，否则 per-user NSS store 更新不了。

可扩展但不越权。 内置 system addon 总是先加载，然后按顺序加载 OPENSANDBOX_EGRESS_MITMPROXY_SCRIPT 里的逗号分隔 mitmproxy addon。addon 拥有完整 L7 hook 面，但只能在内置行为之上，不能在其之前。

链式上游代理 fail-closed。 设置 OPENSANDBOX_EGRESS_UPSTREAM_PROXY 后，所有被 mitmproxy 处理的出向流量经 CONNECT 走代理。规则很硬：endpoint 只接受 host[:port] 或单个 / 路径，host 必须是字面 IP 或带点的域名（无点名字在 Pod resolver 的 search list 下会解析到不同地址，包含集合可能漏掉实际拨号地址）；不能链式代理的流（无 SNI、ignore_hosts 匹配、UDP）被拒绝而不是直连；在 dns+nft 下代理 endpoint 只对 mitmproxy 进程可达（UID/IP/端口三重 nft 规则），字面代理 IP 永久 seed 进包含集合，DNS 学到的地址用有界 TTL。

已知边界

文档把这条链路上的坑列得很清楚，读这些比读特性表更有用：

  • 端口 80/443 总是被拦截，只能加有界的额外端口。Vault 绑定匹配目前只在 80/443 生效——额外端口会被解密和记录，但不会注入凭据。
  • IPv6 与 IPv4 一起拦截（监听器与重定向规则覆盖两个地址族）。
  • 代理未初始化时可见：sidecar 返回 503 mitmproxy not ready，而不是让流量未经检查地通过。
  • SSE 超过约 1 MB 且源站以 TCP RST 关闭连接时可能被截断——这是标准 TCP 语义，不是拦截 bug。
  • 与透明 mesh sidecar 不兼容：Istio/Envoy 这类注入会与 egress 争抢同一命名空间的出向改写，per-sandbox 策略、透明 MITM、Credential Vault 都不能依赖。文档建议把沙箱 Pod 排除在 mesh 注入之外，或用 CNI 级的机制。
  • gVisor 不支持：两条重定向路径都需要的 nftables 特性在 gVisor 里没有。要用安全运行时请用 Kata。
  • OSEP-0023 的实验性 revision runtime（OPENSANDBOX_EGRESS_EXPERIMENTAL_REVISION_RUNTIME）是开发专用开关，默认关。它有一条非常保守的失败策略：任何不确定的结果（未确认的变更、会话清理失败、子进程异常退出）都会锁存为「需要恢复」的粘滞状态，readiness 下降、nft 写入静止、并安装独立的隔离表直到进程生命期结束；重启 sidecar 不算已验证的恢复，应当销毁并重建沙箱。

最后一条读起来沉重，但它是对的方向：涉及 TLS 拦截与凭据注入的子系统，宁可要求重建沙箱，也不要假装恢复成功。

关闭时会发生什么

关闭不是一个瞬间动作。sidecar 会保持 DNS 与网络规则工作，等在途投递完成（有界窗口），然后才移除规则并刷新遥测。Docker 给 sidecar 9 秒停止预算。

投递是尽力而为：强制终止可能丢事件。supervisor 负责以指数退避重启，带崩溃循环断路器，并在新启动前清理陈旧重定向。

可观测性：拒绝原因要分开计

配置了 OTLP 端点时，sidecar 按沙箱导出指标：被拒请求数、DNS 查询结果、nftables 更新失败、进程资源使用。

其中一条设计注意被文档单独点出：「被策略拒绝」与「解析器失败」是两个刻意分开的计数器，因为对错误的那个告警会把诊断结论完全颠倒。一个是策略正常工作，一个是系统坏了。

基数也是有界的：查询的域名与目的地永远不成为 label。

本章要点

  • egress 与沙箱共享网络命名空间，执行点在数据路径上；只有 sidecar 持有 NET_ADMIN。
  • 两层执行：DNS 过滤（便宜、只按名字）与 dns+nft（包级默认拒绝，DNS 学到的地址有界租约）。
  • 优先级固定：平台 deny → 平台 allow → 用户策略；端口地板作为 always-deny 排在用户规则之前。
  • 端口范围规则只支持 TCP、每规则 ≤256 端口、不能与域名组合；无 target 的 allow 对 DNS 层不可见。
  • 透明 TLS 拦截把 CA 投递进信任库而不是关闭校验；链式上游代理 fail-closed。
  • 与 mesh 注入、gVisor 不兼容；已知截断与端口限制写在文档里而不是藏着。
  • 关闭时保持规则直到在途投递完成；崩溃由 supervisor 退避重启并清理陈旧重定向。
  • 被拒与解析失败分开计数，label 基数有界。

凭证保管：让 Agent 用得上密钥，却拿不到密钥

第 11 篇留下的口子在这里补上。

Agent 要干活就得调外部服务：模型 API、Git 托管、制品库、内部微服务。这些都要密钥。但如果密钥进了沙箱，它就同时进了环境变量、命令行、文件系统和日志——而这四样都是模型生成代码可以读取、也可以在不经意间送出去的地方。一次提示注入就足够把它带走。

Credential Vault 要解决的就是这个矛盾：工作负载能发出已认证的请求，但自己不持有凭据。

请求流：谁在什么时候注入

一次完整流程是六步：

1. 生命周期服务器给沙箱挂上 egress sidecar
2. 宿主机侧 SDK 把凭据与绑定写进 sidecar 的 Credential Vault API
3. 沙箱进程用假值或空值运行（例如 ANTHROPIC_API_KEY=fake）
4. 沙箱发出 HTTPS 请求，sidecar 的透明 MITM 检查请求元数据
5. 若恰好一个绑定匹配 scheme/host/port/method/path，注入认证头与占位符替换
6. 响应与 vault 读取接口中的秘密值被脱敏

第 3 步是这套设计的核心技巧：工具链以为自己有密钥。Claude Code、git、curl、npm 都不需要改配置，它们照常从环境变量读一个值，只是那个值是假的；真正认证发生在沙箱外面。文档把它总结成一句：CI 与工具正常工作流不变，秘密不进沙箱的环境、命令行、文件系统与日志。

有一段实现细节很值得学。MITM 进程用的活跃 vault 通过 sidecar 内的本地 Unix domain socket 提供，沙箱工作负载无法经普通代理路径取到。每次新流用缓存的不透明快照 tag 带 If-None-Match 去条件读：

  • 304 Not Modified 复用同一份不可变进程内快照，不渲染也不传输秘密值；
  • 200 OK 带回完整校验过的新快照与新 ETag；
  • 创建与 patch 的响应只有在 store 已经改掉 tag 之后才确认，所以下一个流立刻看到新凭据，没有 cache-TTL 延迟。

不透明 tag 与公开的 vault revision 是两件事：删掉再重建 vault，公开 revision 可能回到 1，但重建后的 vault 拿到的是不同的 tag，不可能复用已删除快照里的明文。

这个依赖是硬依赖

文档在这里用了一个很重的警告，值得完整理解：私有活跃 vault socket 不只是「匹配绑定时才需要」，而是对所有被 Credential Proxy 拦截的流量都是硬可用性依赖。

任何超时、连接拒绝、意外 EOF、5xx、畸形快照、非法 ETag，都会清掉受影响明文缓存，并在任何上游转发之前 fail closed：

  • body 小且已被安全缓冲的请求，收到本地 503；
  • 已开始流式传输、可能跨过阈值、或长度未知的请求，直接断开，因为 mitmproxy 在流式传输开始之后无法安全地合成一个本地响应。

这条约束把「凭据保管」从纯功能变成了数据面可用性的一部分：运维必须监控 sidecar 与那个私有 socket。这是一个诚实的取舍——宁可 503，也不要「没注入凭据的请求」被悄悄放行。

五种认证方式与占位符替换

绑定的 auth 描述凭据如何被渲染进出向请求：

类型 效果
bearer Authorization: Bearer <credential>
basic Authorization: Basic <credential>（值必须已是 base64 的 user:pass）
apiKey 把值注入指定头名（如 x-api-key）
customHeaders 多个头，各自由不同凭据支撑
passthrough 不注入头，配合 substitutions 用

passthrough 存在的原因很实际：有些上游 API 要凭据在路径、查询串或 body 里，而不是头里。所以有占位符替换：

auth={"type":"passthrough",
      "substitutions":[{"credential":"client-secret",
                        "placeholder":"__client_secret__",
                        "in":["body","query"]}]}

替换默认关闭，且是精确、字面、大小写敏感的。四个面各自的行为：

  • path：替换后 URL 编码；若重写后的路径出现歧义段、编码分隔符、或像遍历的内容，sidecar 拒绝请求，而不是把带秘密的 URL 转发出去；
  • query：URL 编码；
  • header：排除逐跳与安全敏感头（Host、Content-Length、转发头）；替换在注入 auth 头之前运行，所以不会重写自己刚创建的凭据头；
  • body：只处理 UTF-8；JSON 按 JSON 字符串内容编码（占位符要放在引号内）；form-urlencoded 按表单编码；压缩体与 multipart 跳过。

还有一条「不二次扫描」的规则：一层的所有替换都基于原始请求文本一次完成，插入的值不会被再扫描一遍。这样避免一个秘密意外改写另一个秘密。body 被重写后会更新 Content-Length 并移除 Transfer-Encoding，因为转发出去的已经是定长的缓冲体。

路径歧义守卫

这是全章最精细的一段。sidecar 只对「本来会收到凭据注入」的请求检查路径。以下情况返回 403：

  • 路径在任意百分号解码深度上包含点段（..）或反斜杠（\、%5c）；
  • 百分号解码在守卫的迭代上限内不收敛。

理由是这些是遍历或路径混淆原语，合法客户端不会发。

但编码斜杠（%2f，含 %252f 这类嵌套形式）是允许的——只要路径的每一层解码都匹配同一个绑定。这个例外不是妥协，而是必要：npm 的作用域仓库路径（/@scope%2fname）和某些内部 pypi 代理的双重编码下载 URL（pkg%252F1.0）就长这样。如果一刀切禁止，正常包安装会坏；而如果放任不管，解码可能跨出绑定边界。规则因此写成「每层解码都必须落在同一绑定内」。

失败方式也分层：小且 body 已知的请求返回 403；超过 mitmproxy 流式阈值（约 1 MiB）或长度未知（chunked）的请求无法在流式传输时合成 403，sidecar 直接断开连接。两种情况都保证请求从不被转发到上游。

要求与它的历史痕迹

Vault 的前置条件写得很具体，每一条都能看出踩过的坑：

  • 服务器要设 [egress].mode = "dns+nft"。只有 DNS 过滤时 Vault 拒绝激活，因为直连 IP 可以绕过 DNS 策略。
  • 创建请求必须带出向网络策略，并且应当用 defaultAction="deny"，显式允许每个绑定引用的主机。
  • defaultAction 默认允许（default-allow）在兼容期内仍被接受，但会发安全警告，并计划在未来收紧。文档的建议是迁移到 deny。
  • 沙箱 Pod 不能同时注入透明 mesh sidecar。
  • 镜像里要有真正要跑的工具（Claude Code 需要 Node/npm 的镜像）。

第 3 条是一个典型的「兼容期设计」：既不能立刻拒绝旧写法的用户，又不能假装它是安全的，于是既接受又警告，并公开了收紧意图。

暂停/恢复：Kubernetes 上会丢，Fast Sandbox 不会

这条差异非常具体，必须分清：

Kubernetes 容器后端：vault 是 egress sidecar 的进程内内存，不在沙箱 rootfs 里，也不在 BatchSandbox Pod 模板里。暂停会删 Pod，恢复后的新 sidecar vault 是空的。恢复后必须由可信客户端重新创建凭据与绑定，才能继续注入。

文档给了配套的操作纪律：把原始 vault 请求或等效的 secret-manager 引用保存在沙箱之外的可信控制面；沙箱回到 Running 后、在允许依赖这些凭据的工作之前，重新调用 create。不要把真实凭据值放进沙箱 metadata、环境变量、快照或日志。

Docker 的 pause/unpause 保留容器进程，但 egress sidecar 的替换或重启同样会产生空 vault。

Fast Sandbox：vault 由 egress 持有：服务器经 FastPath handler relay 把完整 vault revision 推给 egress，relay 响应就是同步的 egress 校验确认。vault 持久化在 egress 本地（内存 + 每沙箱一个明文 v1 文件，放在 Pod 作用域的 emptyDir），所以：

  • Pod 内的 egress 容器重启，Fastlet 重放绑定时可本地恢复；
  • Kubernetes 暂停/恢复会把 vault 文件带进快照 bundle（teardown 之前严格导出，恢复时重新打上运行时围栏再导入）。

代价是那个卷进入凭据信任面：用 medium: Memory 挂载可以让明文不落节点磁盘。文档原话是「vault 卷是凭据信任面的一部分」。

这条对比是全书里「同一契约、不同后端语义」最尖锐的例子之一：同样叫「恢复沙箱」，一个要求你重新注入凭据，一个自动带着走。第 3 篇的兼容性表就是为了避免这种差异变成线上事故。

验收与配置的安全旋钮

sidecar 有三个与 TLS/作用域相关的环境变量，都是默认关：

变量 作用
OPENSANDBOX_EGRESS_CREDENTIAL_VAULT_REQUIRE_TLS 写操作要求 TLS、loopback，或来自受信代理的 X-Forwarded-Proto: https
OPENSANDBOX_EGRESS_CREDENTIAL_VAULT_TRUSTED_PROXY_CIDRS 哪些对端有权断言 X-Forwarded-Proto，其他来源的转发传输头一律忽略
OPENSANDBOX_EGRESS_CREDENTIAL_VAULT_REQUIRE_SCOPED_MATCH 每个绑定必须显式给非空 match.methods 与 match.paths，且不能用 /*

本章要点

  • Vault 让工作负载发出已认证请求但自己不持有凭据；工具链用假值运行。
  • 活跃 vault 经 sidecar 内 Unix socket 提供，沙箱无法经代理路径取到；不透明 tag + 条件读避免重复传输秘密。
  • 这个 socket 是全部被拦截流量的硬依赖，异常一律 fail closed（小 body 503，流式直接断开）。

状态机：暂停、恢复、快照与过期

前十二篇讲的是「怎么把沙箱跑起来」。这一篇讲它怎么结束、怎么暂停、怎么回来。

在沙箱平台上，这些问题的答案会直接决定成本。一个只顾创建的实现，会让空闲沙箱吃掉整个集群；一个只顾回收的实现，会让用户的工作现场凭空消失。OpenSandbox 的答案由四个独立机制拼成：绝对过期、暂停/恢复、快照、以及访问驱动的续期与空闲暂停。

过期是绝对的

创建时的 timeout 是一个绝对 TTL，不是空闲超时。文档写得很明确：服务器或运行时重启都不会重置它，所以沙箱寿命可以只从创建时间推算、可审计。

这条规则有两个推论。

第一，暂停不延长寿命。文档原话是「expiration remains the original request-time clock reading plus that timeout; pausing and resuming do not extend it」。所以一个沙箱不会因为被反复暂停而永生。

第二，续期 API 可以缩短。POST /sandboxes/{id}/renew-expiration 设置的是一个绝对时间 expiresAt——它可以早于、等于或晚于当前值，只要还在未来。server.max_sandbox_timeout_seconds 只限制创建时的 timeout，不限制续期。

这条反直觉的语义有个实际陷阱，文档专门点了：SDK 的 renew(duration) 算的是 now + duration，不是 current expiresAt + duration。如果还剩 30 分钟，你「续期 5 分钟」，实际是把寿命砍短了。需要「只延长」的调用方必须自己先读当前值。

第 9 篇的 mini_osb.py 里 expires_at() 就是这条规则的十行实现：now + timeout，暂停不动它，扫描只看它。

暂停/恢复：三种后端，三种代价

Docker Kubernetes 容器 Fast Sandbox
暂停做什么 容器级 pause（先冻结主容器，再冻结 sidecar） 提交 rootfs 为 OCI 镜像并推送、释放 Pod 与池槽位 检查点写入 artifact store，释放 Fastlet 容量
恢复做什么 容器级 unpause（先解 sidecar） 改写 template 为最新快照镜像、重建运行时 在任意 Fastlet 恢复检查点
保留什么 内存与进程现场 rootfs（内存默认不保留，QEMU 模式例外） rootfs + vmstate + 内存
恢复后地址变吗 不变（同一容器） 变，需要重新解析 endpoint 变（可能换宿主机），必须重新解析
限制 无特殊限制 replicas=1 无特殊限制
算力足迹 保留（进程被冻结） 释放 释放

这张表说明「暂停」在三种后端上不是同一件事。Docker 的 pause 只是冻结，不省内存；Kubernetes 与 Fast Sandbox 才是真的把算力还回去。

第二行的顺序值得再提一次：暂停先冻结主容器、再冻结 sidecar；恢复先解 sidecar、再解主容器。因为主容器一解冻就会发网络请求，此时 egress 必须已经在工作。

快照不是暂停。 文档为 Kubernetes 后端把两者分得很清楚：暂停是内部机制，目的是释放算力并保留连续性（同一沙箱 ID）；快照是公开产物，目的是把状态变成可复制的起点（新沙箱 ID）。两者共用一部分提交机制，但语义不同。

Fast Sandbox 里这个区分同样成立：暂停写检查点并释放 Fastlet；快照把那套机制发布成模板可用的制品，从快照创建出来的是新沙箱——「快照是起点，不是延续」。

持久性到底由什么保证

这是本节最重要的一段，因为它决定了「暂停能不能当备份用」。

对 Kubernetes 后端的 rootfs 快照：只有快照达到 Succeed 且镜像已推到配置的 registry，root 文件系统才是持久的。一个被接受的暂停请求、或处于 Pending/Committing 的快照，不提供任何持久性保证。

之后发生的更改留在容器的可写层里，并且不会在以下情况自动快照：进程退出、容器 OOM 被杀、Pod 进入 Failed、Pod 被驱逐、节点不可用。生命周期 API 目前不提供「故障后快照」或「故障后恢复」操作，Kubernetes 重启产生的新容器也不继承旧的可写层。

文档还提到一条「尽力而为」的运维救急路径：image-committer 有时能在容器元数据与可写快照还在源节点上时，直接从 containerd 读已停止的容器。但它明确声明这不是受支持的持久性契约——containerd/kubelet 的 GC、Pod 替换、节点丢失、容器身份复用都可能让旧层不可用或不可辨识。

结论很实用：需要跨异常存活的数据放持久卷或外部服务；需要可复现的环境状态就显式做 rootfs 快照。挂载卷里的文件按该卷自己的持久与备份行为走，不包含在 OCI rootfs 快照里。

访问驱动的两个方向

「过期」是减法，「续期」是加法。上游把这件事做成了两个独立机制，方向相反但共用「访问即信号」。

renew-on-access（OSEP-0009）：访问延长寿命。它有两个触发源——服务器代理请求、以及经 Redis 投递的 ingress 网关事件。按沙箱 opt-in 由创建时的 lifecycle.renewalPolicy 控制；旧的 extensions["access.renew.extend.seconds"] 在整个 1.x 期间仍受支持。

空闲暂停（OSEP-0024）：不访问就省算力。创建时声明：

"lifecycle": { "idlePolicy": { "idleTimeoutSeconds": 600, "onIdle": "pause", "wakeOnAccess": true } }
  • 有 idleTimeoutSeconds：空闲 X 秒后自动暂停；
  • 没有：只做「唤醒型」策略，不主动暂停；
  • wakeOnAccess: false：保持「只能手工恢复」的旧行为；
  • 省略整个 idlePolicy：完全保持今天的行为。

服务器侧的实现在 integrations/idle_pause/ 下，模块划分能看出设计：activity（记录活动）、decision（判定是否空闲）、executor（执行暂停）、inventory（枚举沙箱）、locking（分布式锁）、probe（探针）、sweeper（周期扫描）、redis_client。

probe 与第 10 篇的 OpenSandbox-Skip-Activity: skip 哨兵是一对：探针不能重置它自己测量的时钟。文档对这个哨兵的安全分析很干脆——伪造它只会伤到自己，因为你的沙箱会显得更空闲、更可能在使用中被暂停，而下一个普通请求会把它唤醒。

这就是「自动暂停」能被接受的前提：恢复必须是自动且便宜的。如果唤醒需要人工，空闲暂停只会制造事故。

客户端侧的池：把创建挪到前面

还有一个与时间强相关的机制不在服务端：SDK 里的客户端沙箱池（实验性，Python/JS/Kotlin/Go 有，C# 暂缺）。

它池化的不是 Sandbox 对象，而是预热好的、状态为 Ready 的沙箱 ID。两个并发流程：

  • 预热（仅 leader）：后台 reconcile 循环在持锁节点上计算空闲缺口并补齐，空闲成员带 TTL 放进状态存储；
  • 取用（任意节点）：acquire() 从存储弹出空闲 ID，连上客户端，可选健康检查与 renew() 到调用方给的超时，然后交给调用方。

三个性质值得记住：

  1. 没有 release()。 沙箱是短命的；acquire() 返回后它就归你，直到你 destroy()/kill()。
  2. max_idle 限制的是暖缓冲，不是借用中的沙箱数量，也不是 DIRECT_CREATE 兜底创建的数量——池不是并发限流器。
  3. AcquirePolicy 决定空池行为：FAIL_FAST（最多试一个）、DIRECT_CREATE（默认，现建）、RETRY_NEXT_IDLE、RETRY_NEXT_IDLE_THEN_CREATE；max_acquire_retries 默认 3，限制的是总候选尝试数，不是额外重试次数。

第 2 条和第 3 条合起来回答了一个常见误解：池化不会让你的沙箱变少，只会让你的等待变少。要控制资源，得靠 TTL、空闲暂停和配额。

失败语义的细节

状态机在边界上的行为，往往比正常路径更能说明设计质量。文档给的清单：

  • 重复暂停 → 409；对非运行态恢复 → 409。
  • 删除后恢复 → 404（不是「悄悄复活」）。
  • Kubernetes 删除：DELETE 返回 204 且 SDK 的 kill() 在删除被接受时返回；之后轮询 GET 会看到 Stopping，清理完成后变 404。用 Noop 回收策略的池会保留进程，所以那个 404 不确认运行时已终止。
  • Docker 并发冲突：删除进行中、或容器已不在暂停/恢复所需状态 → 409；主容器不存在 → 404；sidecar 失败与回滚失败保留 500。
  • Fast Sandbox：只有 Ready 运行时可以暂停；UID 不匹配或缺少检查点 → 409。

「404 不代表进程死了」这条尤其值得记住。它是异步删除的必然产物，也是第 17 篇运维讨论里最容易误判的一处。

本章要点

  • 过期是绝对 TTL：重启不重置、暂停不延长；renew-expiration 设置绝对时间，可以缩短；SDK 的 renew(duration) 从 now 算。
  • 暂停在三种后端上含义不同：Docker 冻结、Kubernetes 提交 rootfs 并释放 Pod、Fast Sandbox 检查点并释放 Fastlet。
  • 暂停 ≠ 快照：前者释放算力保连续性（同 ID），后者产出可复用起点（新 ID）。
  • 持久性只由「快照 Succeed + 镜像已推送」保证；异常终止不会自动快照。
  • 续期与空闲暂停是一对反向机制，都建立在「访问即信号」上；空闲暂停的前提是唤醒必须自动。
  • 客户端池池化的是沙箱 ID，没有 release()，max_idle 不是并发上限。
  • 失败语义要按后端记：重复暂停 409、删除后恢复 404、404 不代表进程已死。

身份与多租户：三种凭据，两种隔离

到这一篇为止，「谁在操作」这个问题一直被我含糊带过。现在要把身份拆开。

OpenSandbox 里至少有三种凭据，它们保护的东西完全不同：

凭据 传输方式 保护的对象
生命周期 API key OPEN-SANDBOX-API-KEY 头 管理沙箱（创建、删除、暂停、续期）
execd 访问令牌 X-EXECD-ACCESS-TOKEN 头或 PTY 子协议 进入沙箱执行命令、读写文件
endpoint 头（secure access / sidecar auth） endpoint 响应里下发 访问沙箱内服务，或调用 egress 策略接口

这三者不可互换。文档在数据面契约里专门写了一句：不要硬编码 execd 地址，也不要假设「生命周期 API key 单独就能授权直连沙箱」。这句话是整篇的基础——「能管理沙箱」和「能进入沙箱」是两个权限。

单租户：一把 key 与它的启动断言

最简单的形态是一把 server.api_key。设置后，除 /health、/version、/docs、/redoc、/openapi.json 之外的所有端点都要求这个头。

没设置时会发生什么，第 4 篇讲过一半：非交互环境（Docker/Kubernetes/CI）必须显式设 OPENSANDBOX_INSECURE_SERVER=YES 才允许启动，交互式 TTY 则要求输入 YES，30 秒超时。

这个设计的价值不在「防止误配」而在「让误配可见」。一个无认证的服务器不会在某个请求上失败，它会在每个请求上成功，直到有人读到不该读的东西。

多租户：把身份交给提供方

多租户是可选、且仅 Kubernetes 支持的。Docker 模式下配置了 [tenants]，服务器会以 fatal error 拒绝启动。

请求路径变成：

OPEN-SANDBOX-API-KEY
  → 租户提供方查 key
      找到   → 注入 tenant context，路由到该租户命名空间
      没找到 → 401
  → （未配置租户时）回落到 server.api_key 校验

具体六步（文档的编号）：

  1. 认证中间件通过提供方把 API key 解析成 TenantEntry；
  2. 租户命名空间写进请求作用域的 ContextVar；
  3. 生命周期操作（create/list/get/delete）使用解析出的命名空间；
  4. list 只返回已认证租户命名空间里的沙箱；
  5. 代理路由（/sandboxes/{id}/proxy/...）在多租户模式下也要求 API key——这是与单租户的一个行为差异，文档专门用提示框标了出来；
  6. 创建时在工作负载上打 opensandbox.io/tenant=<name> 标签。多个租户共享一个命名空间时，list/get/delete/proxy 会隐藏其他租户的带标签沙箱（返回 404），未打标签的历史沙箱在过期前仍然可见。

第 6 条值得多想一步。它说明隔离有两层：命名空间级的硬隔离，以及共享命名空间时的标签级软隔离。软隔离的失败模式是「历史沙箱泄漏到别人的列表里」，而它们的处理方式是让它自然过期——这是一个有意的、写进文档的取舍（迁移期不能把老沙箱变成不可见）。

身份为什么放在提供方

租户来自 TenantProvider，不是服务器配置。两个实现：

  • file：本地 TOML，改动热重载约 2 秒；
  • http：远程端点，按 TTL 缓存，端点不可达且缓存超过 max_stale_seconds 时返回 503 TENANT_PROVIDER_UNAVAILABLE。

文档给的理由是「身份住在提供方里，租户管理就留在拥有身份的平台那边」。这条设计判断很重要：租户列表通常已经存在于某个 IAM 或内部平台，把它抄一份到沙箱服务器配置里，等于制造第二个事实来源。

三个启动期断言把这条设计锁住：

  • [tenants] 与 server.api_key 不能同时存在（启动报 "Remove server.api_key from server.toml"）；
  • 每个租户的 API key 必须唯一（重复 key 启动报错）；
  • 每个可枚举的租户命名空间必须存在且可访问（Kubernetes 后端启动时逐个校验，失败则 os._exit(1)）。

第三条的实现细节还留了一个例外，注释写得很清楚：fsb 的 CR reader 是惰性的，不能让一个纯 legacy 部署在启动时被它拖住，所以那条路径跳过直接校验，改为首次读取时检查集群凭据与 CR 权限。

隔离模型：服务器不承诺它做不到的事

多租户文档里有一句话很干脆：服务器本身不执行资源配额或网络策略，隔离委托给 Kubernetes。

维度 机制 作用域
资源配额 ResourceQuota 每命名空间 CPU/内存/存储
默认限额 LimitRange 每命名空间默认容器资源
网络隔离 egress sidecar 每沙箱出向策略
沙箱数量 ResourceQuota（Pod 数） 每命名空间 Pod 上限
RBAC RoleBinding 每命名空间 API 访问

还有一条必须点出来的现状：池管理路由（/pools）目前不是租户作用域的，它们在服务器配置的默认命名空间里操作。池是共享资源。需要每租户池隔离的部署，要么拆成多个服务器实例，要么等后续支持。

这条「不是租户作用域」的声明比任何功能列表都有价值：它明确告诉你哪里的多租户假设不成立。

Fast Sandbox 的租户映射

Fast Sandbox 的租户处理是另一套实现：租户提供方把每个已认证租户映射到一个 fast-sandbox 命名空间。请求作用域的操作从 context 解析命名空间；后台工作（没有请求 context）则回落到按沙箱 ID 反查。

这个回落是必要的，也是风险的来源：后台的 janitor、空闲暂停扫描、快照收敛都拿不到请求上下文，只能靠「沙箱属于谁」的数据反查。所以那条数据必须准确——这也是为什么第 8 篇强调「CR 是意图与放置的事实来源」。

命名空间不是唯一边界

读这一章时要抵抗一个诱惑：把「一个租户一个命名空间」当成完整的隔离。它不是。

  • 同一个命名空间内的租户之间只有标签级软隔离（上面第 6 条）；
  • execd 的 /v1/filesystem/{uid}/{gid} 身份切换解决的是同一沙箱内多会话的权限问题，文档明确写它不是租户隔离边界；
  • secureAccess 的 endpoint 头是访问凭据，不是身份——它不区分「谁在调用」，只证明「你有权访问这个端口」；
  • Credential Vault 隔离的是秘密，不是身份。

这四条合起来说明：这个平台的身份模型是分层且不统一的。每一层解决一个具体问题，没有一层假装自己是全局的授权中心。读代码时如果发现某个模块不检查租户，先看它是否在别的层被保护——但也不要假设它一定被保护，这正是第 15 篇要讨论的「隔离边界要为每一层单独验证」。

本章要点

  • 三种凭据保护三种不同的东西：管理沙箱、进入沙箱、访问沙箱服务；不可互换。
  • 无 API key 的启动需要显式确认，目的是让不安全配置可见而不是「尽量可用」。
  • 多租户是可选、仅 Kubernetes；Docker + tenants 直接拒绝启动。
  • 身份住在提供方（file/http），不在服务器配置里；三条例行启动断言锁住配置合法性。
  • 共享命名空间时靠 opensandbox.io/tenant 标签做软隔离，未打标签的历史沙箱在过期前仍可见。
  • 服务器不执行配额，隔离委托给 Kubernetes；池路由目前不是租户作用域的。
  • 命名空间不是唯一边界：文件身份、endpoint 头、Vault 各管一件事，没有全局授权中心。

隔离与加固：从 runc 到 microVM

第 1 篇把「隔离必须是运行时的性质」列为第一条需求。这一篇兑现它，并且要说清一件事：隔离不是一个开关，是一个分层结构，每层能挡的东西不同。

四层，各自挡什么

execd 文档列的四层结构是全书里最清晰的隔离表述：

层 内容 挡什么 谁开启
沙箱边界 资源限制、身份、隔离运行时（runc/gVisor/Kata/Firecracker） 容器逃逸、越权访问宿主 创建时选定
加固地板 原生 launcher：drop capabilities、no_new_privs、syscall 拒绝列表、Landlock 写限制 沙箱内部的提权与持久化 运维开启
隔离会话 per-execution bubblewrap 命名空间 同一沙箱内任务之间的相互影响 每次执行
eBPF 审计 记录 exec / connect / 权限变更 事后取证（不阻断） 单独 execd-ebpf 构建

关键设计不是这四层的存在，而是每层都会报告自己的状态：active、degraded 或 unsupported。客户端能验证实际生效的是哪几层，而不是相信宣传。

第 9 篇提过的那条边界要重复一次：execd 的生命周期钩子是平台配置的可信代码，在沙箱内运行。文档原话是「它们是便利，不是安全控制」。任何把初始化工作当安全边界的方案都会在这一句上翻车。

安全运行时：一次配置，全局生效

隔离运行时由服务端配置，[secure_runtime] type 取 ""（runc，默认）、gvisor、kata、firecracker。文档给的开销对照：

运行时 隔离机制 启动开销 内存开销
runc（默认） 进程级 cgroup ~0 ms 极小
gVisor 用户态内核（syscall 拦截） ~10–50 ms ~50 MB
Kata（QEMU） QEMU 虚拟机 ~500 ms ~20–50 MB
Kata（Firecracker） microVM ~125 ms ~5 MB
Kata（CLH） Cloud Hypervisor ~200 ms ~10–20 MB

配置翻译成后端参数，由 runtime_resolver.py 完成：

DEFAULT_DOCKER_RUNTIMES = {"gvisor": "runsc", "kata": "kata-runtime"}
DEFAULT_K8S_RUNTIME_CLASSES = {"gvisor": "gvisor", "kata": "kata-qemu", "firecracker": "kata-fc"}

Docker 上是一条 OCI runtime 名字，Kubernetes 上是一个 RuntimeClass。调用方完全看不到这个差异——这正是第 5 篇「运行时中立」的含义。

启动时会校验声明的运行时可用（validate_secure_runtime_on_startup）。不可用就启动失败，理由还是第 4 篇那条：隔离配错时，单个请求看不出来。

兼容性矩阵：选型时真正要看的东西

secure-container 文档给了一张很实用的表，它比「启动开销」更能决定选型：

特性 runc gVisor Kata(QEMU) Kata(CLH) Kata(FC)
syscall 兼容性 完整 部分 完整 完整 受限
GPU 是 是* 是 是 否
IPv6 是 是 是 是 是
特权模式 是 是 是 是 否
Docker 卷 是 是 是 是 是
systemd 是 是* 是 是 否

* 表示需要额外配置。

这张表解释了为什么没有「最佳运行时」：Firecracker 密度最高、开销最低，但 syscall 受限、没有 GPU、不支持特权模式与 systemd。要跑一个需要 systemd 或 GPU 的镜像，就不能用它。

跨组件的硬性不兼容

这是本章最重要的部分：几条隔离选择会直接让某些功能失效，而这些约束分散在不同的文档里。

gVisor × egress。 egress 的两条重定向路径（iptables 与原生 nftables）都需要 gVisor 不支持的 nftables 特性。文档的结论是「两者都不行」：要安全运行时 + 出向策略，用 Kata。

gVisor × rootfs 快照。 docs/api/implementation-compatibility.md 写明：Kubernetes 的 rootfs 快照提交器拒绝 gVisor RuntimeClass。也就是说，选择 gVisor 会同时失去「默认出向策略」和「暂停/恢复」两项能力。

egress × mesh 注入。 透明 mesh sidecar（Istio/Envoy）与 egress 会在同一命名空间里争抢出向改写。文档给了三条出路：把沙箱 Pod 排除在注入外；保留注入但不启用 egress 的凭据与策略功能；把出向策略移到沙箱 Pod 之外的平台机制。

Fast Sandbox × guest netfilter。 跨 VM netns 的流量从 Pod 视角是二层桥流量，所以权威执行层是 pod-netns 的 forward 链，不是容器 OUTPUT 路径。第 8 篇讲过这条，它解释了一个反直觉的现象：guest 自己的 iptables 不是执行点。

Firecracker × 宿主能力。 需要 /dev/kvm、/dev/net/tun、cgroup v2、XFS reflink、足够大的 /dev/shm，以及 10 GiB 磁盘 / 2 GiB 内存的余量。缺任何一项，节点不会被标记，也不会收到 microVM 沙箱。

把这些放在一起看，选型其实是一张能力取舍表，而不是一个安全等级排序：

要 GPU / systemd / 特权模式        → Kata(QEMU) 或 runc
要最高密度 + 最低开销               → Firecracker（放弃 GPU 与 systemd）
要 syscall 兼容 + 低开销           → gVisor（放弃 egress 包级策略与 rootfs 快照）
要一切功能都能用                    → runc（放弃强隔离）

加固地板：默认关闭的正确性

加固地板指的是 execd 的原生 launcher：每次启动用户进程时 drop capabilities、设 no_new_privs、装 syscall 拒绝列表、用 Landlock 限制文件系统写。

它默认是关闭的（由运维开启）。这个默认值我认为是对的，理由是顺序问题：加固地板会改变进程能做的事，而用户镜像的假设可能是「我有完整 syscall」。把它默认打开，会让一大批现有镜像在运行时报奇怪的错误——而这些错误会被误诊为平台 bug。

正确的默认是「隔离边界先到位（运行时），加固地板按需开启（策略）」，而不是反过来的。这也解释了为什么文档强调「每层报告自己的状态」：当加固地板开启后某个镜像坏了，你要能立刻看出是哪一层变的。

隔离能挡什么，不能挡什么

把这一章收紧，需要一份诚实的威胁模型。根据前面的材料，可以列出：

能挡住的：

  • 容器逃逸到宿主（取决于运行时强度）；
  • 沙箱之间互相访问（命名空间 + 私有 CIDR 的同级隔离规则）；
  • 从内部关闭或绕过网络策略（沙箱没有 NET_ADMIN，规则在 sidecar/共享 egress 里）；
  • 拿到真实凭据（Vault 把秘密留在沙箱之外）；
  • 同一沙箱内不同任务互相影响（隔离会话的 per-execution 命名空间）。

挡不住的：

  • 通过被允许的出向目标泄露数据。策略允许 pypi.org，那么沙箱就能向 pypi.org 发数据。域名白名单是目的地控制，不是数据流控制。
  • 提示注入导致的沙箱内恶意行为。隔离限制的是「能碰到什么」，不是「会做什么」。一个被注入的 Agent 可以合法地删掉自己的工作区。
  • 跨租户共享命名空间时的软隔离绕过（如果部署选择了共享命名空间）。
  • eBPF 审计的缺失（默认镜像不含它）。
  • 生命周期钩子里的错误（它们是可信代码，出错就是沙箱内出错）。

这份清单比「我们提供四层防护」有用得多。它也是第 18 篇讨论「这套设计放弃了什么」的输入。

本章要点

  • 四层防护：沙箱边界、加固地板、隔离会话、eBPF 审计，每层自报 active/degraded/unsupported。
  • 隔离运行时由服务端配置，翻译成 Docker OCI runtime 或 K8s RuntimeClass，调用方无感；不可用时启动失败。
  • 兼容性矩阵决定选型：Firecracker 密度最高但 syscall 受限、无 GPU、不支持 systemd/特权。
  • 硬性不兼容要记住：gVisor 不支持 egress 包级策略与 rootfs 快照；egress 与 mesh 注入冲突；Fast Sandbox 的执行点是 pod-netns forward 链。
  • 加固地板默认关闭，因为「先边界后策略」的顺序错误会制造误诊。
  • 隔离挡住宿主逃逸与内部绕过，挡不住「通过被允许的出向目标泄露数据」与提示注入导致的沙箱内破坏。

可观测性与诊断：让失败留下证据

沙箱平台有一个特殊的观测难题：被观测的东西是短命的。一个沙箱活了 90 秒，跑了一堆命令，然后被删掉。它打印的一切跟着消失。如果这时用户说「Agent 报错了」，你手上什么都没有。

OpenSandbox 为此准备了四条互不重叠的证据链：状态与原因码、请求 ID、指标、以及可选的节点级采集。这一篇按「出问题时你会按什么顺序查」来组织。

第一层：状态本身就是证据

最便宜的证据在 API 响应里。沙箱对象带 state / reason / message / lastTransitionAt，四者合起来能回答大部分初级问题：是镜像问题、调度问题，还是我自己操作错了。

配套的还有 diagnostic 契约里的结构化路由上下文：GET /sandboxes/{id}/diagnostics/context 返回运行时后端与后端定义的诊断标识符。

后端 context 内容
Docker 后端名 docker + 容器标识符
Kubernetes 命名空间/工作负载标识符 + 已分配的 Pod 名（如果有）
Fast Sandbox fast-sandbox + 空标识符 map

第三条的「空 map」不是缺陷，是诚实：Fast Sandbox 的运行时标识不在 Kubernetes 资源里，适配层拿不到。文档还说明 context 不需要 scope、不依赖 execd 就绪，而且 Kubernetes 的 context 可以在 Pod 分配之前查询。

第二层：请求 ID 把链路串起来

服务器有 RequestIdMiddleware，X-Request-ID 是可选请求头——不传就自己生成。日志、指标、诊断都带这个 ID。

这个机制很小，但它是跨组件排障的前提：客户端报了一个 ID，你才能在控制面日志、ingress 日志、execd 日志里找同一条链路。没有它，「用户说失败了」和「服务端说成功了」这种对话会永远卡住。

第三层：指标，以及它的基数纪律

Go 组件共享一套 OTLP 配置（endpoint、关闭开关、聚合时序），Python 的生命周期服务器另有 [otel] 段。

各组件的指标面不完全一样，我按「谁能回答什么问题」列：

组件 能回答的问题
生命周期服务器 创建延迟、请求量、错误分布（HTTP metrics 中间件）
Kubernetes 控制器 分配路径指标、容量指标，以及 controller-runtime 复用的指标
execd 沙箱 CPU/内存快照与实时流、执行耗时、OOM kill 观测
egress sidecar 被拒请求数、DNS 查询结果、nftables 更新失败、进程资源
ingress HTTP 请求与路由、上游连通性分类
node agent 记录/字节数、有意丢弃、重试、队列深度

其中两条设计纪律值得单独记住。

拒绝与失败必须分开计。 egress 把「被策略拒绝」与「解析器失败」做成两个独立计数器。文档的原话是：对错误的那个告警会把诊断结论完全颠倒。前者是策略在工作，后者是系统坏了——用同一个指标，值班的人永远分不清。

基数要有界。 egress 不把查询的域名或目的地做成 label；node agent 不把沙箱或 Pod 标识做成 label。这两条限制会让某些排查变难（你无法直接按域名聚合），但换来的是指标系统不会因为用户输入而爆炸。这是一个典型的「先保证可用，再用日志补细节」的取舍。

第四层：诊断 API 与它的两种投递

specs/diagnostic-api.yml 定义了一条 best-effort 的证据通道：

GET /sandboxes/{id}/diagnostics/context    后端与标识符
GET /sandboxes/{id}/diagnostics/logs       日志内容描述符（scope 必填）
GET /sandboxes/{id}/diagnostics/events     事件内容描述符（scope 必填）

scope 的取值按后端不同：

后端 logs events
Docker container / all runtime / all
Kubernetes container / all runtime / all
Fast Sandbox 未实现 runtime / all

不支持返回 DIAGNOSTICS_SCOPE_UNSUPPORTED；后端没实现返回 501 DIAGNOSTICS_NOT_IMPLEMENTED；未知沙箱 404。

响应有两种投递方式：delivery: inline 带 content，或 delivery: url 带 contentUrl 与可选过期时间。这里有两条使用纪律，文档写得很直接：

  • SDK 不会去下载 URL 内容；要自己取。
  • 先看 truncated 与 warnings，再决定是否把结果当成完整证据。

第二条是很多排障误判的来源：诊断数据本身可能是截断的，把一个截断的日志当成「全部输出」会得出错误结论。

除了这条契约化的通道，服务器还有一套面向运维与 AI 排障的纯文本 devops 路由（api/devops.py），CLI 的 osb devops 就调用它们。契约通道给程序用，纯文本通道给人（或给读文本的 Agent）用——这个分工很实际。

第五层：节点级采集，让日志活过沙箱

如果沙箱删了就什么都没了，那上面四层都只能在「还活着」的时候用。Node Agent 是补这一块的：一个可选 DaemonSet，每台 Linux 节点一个采集器，watch 该节点上每个沙箱 Pod 的输出并送到持久存储。

它的设计里有四个决定值得学。

源与 sink 是编译期注册表，不是插件。 一个构建嵌入它支持的源，配置只在其中选择；未知名字让 Agent 不 ready 而不是启动一个残缺管道。运行时不加载任何代码。这条设计对供应链安全很重要：一个能动态加载采集插件的守护进程，等于给集群装了一个远程代码执行入口。

队列有界，丢弃策略明确。 默认 block 策略在 sink 变慢时对源施加背压——采集变慢，什么也不丢。另一条 drop 策略更硬地限制内存，并把丢弃记录进流的完整性标记。全局内存预算、每沙箱队列预算、可选每沙箱限速，防止一个吵闹的沙箱饿死整节点。

失败即关闭，绝不崩溃循环。 非法配置、损坏或不匹配的恢复状态、不可用的目标，会让进程活着但不 ready，并报出命名原因。它从不静默重置并重新采集，也从不在未验证的目标上推进进度。

对象布局镜像集群现实。 每条流成为一个对象族：

<cluster>/<namespace>/<sandbox_id>/<pod_uid>/
  sandbox.log
  sandbox.<generation>.log
  sandbox.finalized.<revision>.json

finalized 标记是流的「结案陈词」：一份累积的、不可变的快照，列出每个已关闭对象的 size 与 checksum，消费者可以校验。它回答的是事故之后唯一重要的问题：这些日志我能信吗？

标记状态 含义
complete 没有有意丢弃或已知缺口；至少一次投递仍可能含重复
complete-with-drops 至少一条被有意丢弃，受影响的区间已记录
incomplete 至少一个已知区间读不到，或其覆盖无法证明

这份诚实的代价是「看起来更差」：Agent 重启后恢复的数据照样投递，但下一个标记是 incomplete，因为无法证明一次短命的 rotation 没有在中断期间消失。消费者拿到的是真相，不是乐观。

投递语义是至少一次、绝不静默丢失：游标只在 sink 持久接受且源确认后才推进；finalization 本身是两阶段、可崩溃恢复的事务。重复可能，未记账的丢失不允许。

还有两个运维边界：采集凭据只给 append/read/write，从不给 delete；删除永远走单独的离线工具。保留策略是运维的事，Agent 只采集。桶开了版本控制或 WORM、或存在重叠的生命周期规则，会被当作永久启动错误拒绝——因为那会破坏 Agent 的完整性假设。

一个整体判断

把五层放在一起看，这个项目的可观测性有一个一致的态度：宁可承认不确定，也不给一个看起来漂亮的结论。

证据都带边界：状态带 reason、诊断带 truncated、日志带 complete/incomplete、指标拒绝高基数、指标把「拒绝」和「坏了」分开、SDK 不替你下载 URL。这套态度在实践中意味着更多次「不确定」，但每一次都是可复核的。

本章要点

  • 五层证据：状态与原因码、请求 ID、指标、诊断 API、节点级采集。
  • diagnostics/context 不需要 scope，可在 Pod 分配前查询；Fast Sandbox 的标识 map 为空是诚实而非缺陷。
  • 指标有两条纪律：拒绝与失败分开计、label 基数有界。
  • 诊断 API 是 best-effort：先看 truncated/warnings，SDK 不下载 URL。
  • Node Agent 用编译期源/sink、有界队列、fail-closed readiness 与完整性标记，把「能信吗」变成可校验的字段。
  • 采集凭据没有 delete 权限，保留策略在采集之外。

运维与失败：这套系统承诺什么，不承诺什么

前面十六篇讲的是「它怎么工作」。这一篇讲它在坏掉的时候长什么样。

判断一个基础设施项目的成熟度，最有效的办法不是看功能表，而是看它敢不敢写清「这里会中断」「这里不保证」「这里要人工」。OpenSandbox 的文档在这方面出乎意料地直接，这一篇基本是在整理它的自我限制清单，并补上我的解读。

部署顺序不是建议，是依赖

Kubernetes 部署有固定顺序：

base → opensandbox-controller → fast-sandbox* → ingress-gateway → opensandbox-server → 可选组件

每一步的理由都写在文档里：

步骤 chart 为什么在这个位置
1 base 拥有 sandbox.opensandbox.io 与 sandbox.fast.io 的 CRD 与 RBAC，其他一切都依赖这些对象存在；每集群装一次
2 opensandbox-controller reconcile 你和服务器创建的 BatchSandbox/Pool/SandboxSnapshot
3 fast-sandbox（可选） 必须在 server 之前：服务器的 fsb 配置指向 FastPath gRPC endpoint（fast-sandbox-fastpath...svc:9090），启动时就开始 watch sandbox.fast.io 对象
4 ingress-gateway Kubernetes 部署必需：沙箱 Pod 只有 ClusterIP，客户端流量必须经网关；且要在 server 之前装，服务器才能在首次安装时就宣告它
5 opensandbox-server 生命周期 REST API
6 opensandbox-node-agent（可选） 顺序无关

第 4 条最容易被跳过，后果也最直接：跳过网关，沙箱创建成功但谁也访问不到。文档把它写成「required for Kubernetes deployments」而不是「recommended」。

用 umbrella chart 时这个顺序由 chart 处理。注意它需要先 helm dependency build opensandbox——charts/ 目录在仓库里是 git-ignored 的，每次重建。chart 从 release-X.Y.Z 标签的 checkout 安装，不单独发布 chart 包。

服务器的高可用承诺有多窄

这是全文档里最值得逐字读的一段：

The chart defaults to server.replicaCount: 1. Keep one active Lifecycle Server unless you deliberately use the PostgreSQL-backed Kubernetes public snapshot topology... That exception coordinates public snapshots only; it does not provide general multi-replica Server HA. The Server Deployment uses the Recreate strategy so an upgrade stops the active Server before starting its replacement; expect a brief API interruption during upgrades.

拆开来是四个明确事实：

  1. 默认单副本，升级时会短暂中断 API（Recreate 策略：先停后起，不并存）。
  2. 多副本只有一个合法场景：PostgreSQL + Kubernetes runtime，且只协调公开快照。
  3. SQLite 与 Docker 快照执行不支持这个多活拓扑。
  4. 文档在别处还写了一句更直白的：「General load-balanced lifecycle HA is not supported yet — and is not pretended.」

第 4 条的语言很少见。大多数项目会把「部分多活」写成「高可用」，这里选择把它写成它本来的样子。

顺带一个对比：Controller 的 chart 默认开启 leader election（leaderElection.enabled: true），因为它本来就是 Kubernetes 风格的控制器；而生命周期服务器不是，它没有 leader election，只有「一个副本」这个操作约定。两种风格并存，说明作者没有为了统一而统一。

Fast Sandbox 的失败表

Fast Sandbox 的文档给了一张很干净的失败矩阵：

失败 影响 恢复
控制面重启 短暂失去变更能力；运行中沙箱不受影响 CR 驱动重放意图
Fastlet Pod 丢失 该 Fastlet 上的沙箱中断 按每沙箱 failurePolicy，在 recoveryTimeoutSeconds（默认 60 秒）后处理；默认人工
服务器重启 沙箱无影响；未完成操作从持久记录继续 同一套观察-收敛
制品 store 故障 新启动降级为直接拉取；运行中沙箱不受影响 store 恢复后 DART 继续服务

第二行是唯一的「会丢东西」的情况，而且是默认人工。这是一个刻意的选择：自动把沙箱迁到别的节点，需要先决定「未持久化的写入怎么办」，而这个决定属于业务，不属于平台。

容量规划：三处容易被忽略的账

池容量。 bufferMin/bufferMax 决定稳态快，poolMin/poolMax 决定上限。配小了会频繁 429；配大了会白占资源。文档给的调节旋钮是 maxUnavailable（默认 25%）和池的模板 revision 滚动。

快照的 registry 与保留。 Kubernetes 后端的快照镜像要推到 registry，凭据配在 controller manager 启动参数上（--snapshot-image-uri-template 之类的也在那里），不在 ~/.sandbox.toml。文档专门强调这一点，因为它和大多数人的直觉相反：快照是控制器做的，不是服务器做的。

另外：删除快照记录不会删除已推送的镜像。保留与清理是运维策略，被有意留在沙箱生命周期之外。这意味着如果你不主动清理，registry 会一直涨。

节点状态盘。 Firecracker 的每沙箱 rootfs 是 XFS reflink 的 CoW 副本，所以节点状态根必须在 XFS + reflink 上。文档给了准备步骤（新建空盘 mkfs.xfs -m reflink=1、挂载、blkid、写入 fstab），也给了没有额外设备时的 scripts/fast-sandbox-state-root-setup.sh（用 fallocate 预留空间建 loop 文件系统，拒绝已存在的 backing file、符号链接路径、已挂载目标与非空挂载点，失败时保留文件供检查而不是冒险删除）。

容量口径也写得很实：要按「每个被缓存模板的 rootfs + guest 内存快照 + 活跃沙箱可写数据 + 缓存开销」算，起步留 50% 余量，并保持 > 10 GiB 空闲（默认就绪地板）。

还有一条运维动作容易做错：如果节点已经在跑沙箱，你新挂了状态盘，已运行的沙箱可能还看着旧文件系统。正确做法是先 drain 该节点沙箱，再重启 runtime Pod；或者在部署 runtime DaemonSet 之前就把盘准备好。

三个「已知不可靠」的明确声明

文档里有三处主动说明「这块还没被验证到位」，我认为这是这一篇最重要的内容。

1. Node Agent 的资源默认值没有基准。 数据面文档写明：采集与投递已实现，但生产的资源默认值仍在等 benchmark 与 soak 结果（OSEP-0019），「把 chart 的资源值当作起点」。

2. Fast Sandbox 并发 20 的创建不可靠。 Performance 页写明：并发 20 的延迟分布只含成功的尝试，48 次 SandboxRateLimitException（HTTP 429 / Fastlet CapacityRejected）与 1 次就绪超时被排除；有 4 个测试 CR 卡在删除中，原因是 assignment annotation/status projection 冲突。文档的结论是：这次运行不建立「可靠的 20 路接纳」或「可持续 RPS」，实现层面的原因需要单独修，换宿主磁盘解决不了。

3. 同节点恢复的 62 秒无人解释。 运行时恢复是几十毫秒，但 SDK 侧恢复中位 62.66 秒。文档明确说：日志显示路由在恢复后立刻发布，大部分时间在 endpoint/guest 可用性与客户端等待上；这次测量没有隔离出是网络、网关、endpoint 解析还是重试机制造成的差距，也明确禁止把运行时数字当作 SDK 恢复数字。

这三条的共同点是：它们都给出了「不要用哪个数字做承诺」。这比多写三个功能有用。

升级与镜像可信

两条与升级相关的实践：

镜像按 digest 固定。 发布镜像在三个官方 registry（Docker Hub、GHCR、阿里云 ACR）以同名组件发布；带标签的发布镜像用 Cosign 做无密钥签名并带 provenance 证明。生产要按 digest 固定，并按 docs/community/release-verification.md 对照 OpenSandbox 的 GitHub Actions 身份验证。

旧镜像的坑要记住。 单机网络文档提过一个具体例子：server/v0.2.3 把内部 IP 解析硬编码在两条代理路径里，只设 resolve_internal = false 救不回来，SDK 就绪检查会超时；修好的镜像是 release-1.1.0。文档还提醒 server/v* 这类冻结标签不再标识较新的服务器发布，现在用统一发布标签。

这段的价值在于它示范了「兼容性说明要写到版本号一级」。

排障顺序建议

把第 16 篇的五层证据和这一篇的失败矩阵合起来，我建议的排障顺序是：

  1. 看状态：GET /sandboxes/{id} 的 state/reason/message，先分清是「没创建」「创建了但没就绪」「就绪但访问不到」。
  2. 看条件：Kubernetes 上 kubectl describe batchsandbox，特别是有没有 PoolAllocationPending；Fast Sandbox 上看 sandbox.fast.io CR 的 status.runtime。
  3. 看 endpoint：GET .../endpoints/{port} 的形态是否符合预期（直连/网关/代理），头是否带全。
  4. 看数据面：/ping 是否 200；不行再取 diagnostics/logs，注意 truncated。
  5. 看指标与日志：egress 的「拒绝」与「解析失败」分开看；ingress 的 network-readiness 只看它的影子信号含义。
  6. 查已知限制：并发创建 429、池满、暂停后 vault 为空、404 不代表进程已死。

第 6 步经常被跳过，而它往往是最快的答案。

本章要点

  • 部署顺序是依赖：CRD → controller → (fast-sandbox) → ingress-gateway → server；K8s 下沙箱 Pod 只有 ClusterIP，缺网关等于访问不到。
  • 服务器默认单副本、升级会短暂中断；多副本只允许 PostgreSQL + K8s runtime 且只协调公开快照；SQLite/Docker 不支持。
  • Controller 默认开启 leader election；生命周期服务器没有，靠单副本约定。
  • Fast Sandbox 控制面单副本是设计立场；Fastlet 丢失默认人工恢复（60 秒后按 failurePolicy）。
  • 三处账要单独算：池容量、快照 registry 与保留（删记录不删镜像）、节点 XFS reflink 状态盘与 10 GiB 地板。
  • 文档主动声明三处「未验证到位」：node agent 资源默认值、并发 20 创建、同节点恢复 62 秒。
  • 镜像按 digest 固定并做 Cosign 验证；server/v* 冻结标签不再代表新版本。

权衡：这套设计放弃了什么

前十七篇解释「为什么这么设计」。这一篇做反面：每个设计决定都放弃了什么，以及在什么条件下这些取舍会失效。

我按「影响面」排序，从最结构性的开始。

一、前缀分发换零状态路由

fsb- 前缀决定走哪个后端。

得到的：不需要「sandbox → backend」映射表，因此不需要维护它的一致性，控制面重启也不需要恢复它。

放弃的：显式路由。前缀是隐式契约，被 SDK、文档、运维手册同时依赖；任何一个后端漏加前缀，路由会静默走错分支——不是崩溃，是错误行为。

什么时候失效：出现第三个后端时。两个分支用前缀是划算的，三个就开始需要真正的注册表。

二、一条契约换后端能力差异

得到的：调用方学一次，本地 Docker 到集群可以平滑迁移；SDK 一种实现覆盖全部后端。

放弃的：能力可表达性。类型系统无法表达「这个后端返回的 endpoint 不支持任意 TCP 转发」「这个后端的暂停不保留内存」「这个后端的 vault 在恢复后是空的」。这些差异只能写进 implementation-compatibility.md 和每个后端的指南。

代价落在谁身上：写代码的人（他要读文档），以及维护者（他要在三处同步语义）。

替代方案是能力协商端点。文档明确说当前没有通用能力协商，也承认 OPEN-SANDBOX-ORIGIN 之类的信号「是现有的路由信号，不是通用能力清单」。这是一个诚实的欠账，不是遗漏。

三、预热换请求级定制

得到的：常数时间创建。100 个沙箱 0.92 秒（池化）与 76 秒级（非池化）的对比就是它的价值。

放弃的：每个请求定制环境的能力。entrypoint/env 变成分配后的 task，卷与 networkPolicy 不能与 poolRef 共用，池 Pod 必须满足 task 契约。

额外的代价：数据面必须处理「复用」带来的身份问题。execd 的 per-allocation 绑定、未绑定时业务端点 503、以及 Fast Sandbox 的 subject 状态机，都是为这一条付的账。

什么时候失效：当每个请求都需要不同的镜像或系统依赖时，预热池的价值会被「池里没有我要的模板」抵消。这时候正确的做法是多个池，而不是放弃预热。

四、sidecar 换共享 egress

得到的：单机与 Pod 内隔离干净，每沙箱策略互不影响，工作负载没有 NET_ADMIN。

放弃的：密度。N 个沙箱 N 个 sidecar，每个都要自己的 DNS 代理与规则。

Fast Sandbox 选了另一头：每个 Fastlet 一个 egress 进程，服务 N 个 subject。这换回了密度，代价是执行路径显著变复杂：按源 IP 分发、per-subject nft 链、master 链只标记不发 accept、租约与刷新循环、以及「管理面 endpoint 必须对所有 subject 隐藏」这类细节。

这条权衡没有全局最优解，只有「在什么密度下选哪边」。文档把它写成了两个互斥的 profile，我认为这是正确的处理方式：不假装一套实现能同时最优。

五、fail-closed 换可用性

这个项目在多处选择了「宁可失败，不要降级」：

位置 选择 放弃的东西
启动期检查 没 key / 租户空间不可达 / 安全运行时不可用 → 退出 部分可用性
egress 启动 装不上重定向规则 → 退出，绝不空跑 沙箱可用性（如果有 bug）
egress 重载 解析失败保留上一份已接受规则 「立即生效」
Vault socket 任何异常 fail closed（503 或断开） 请求成功率
OSEP-0023 实验面 任何不确定 → 锁存恢复状态，重启不算恢复 快速自愈

这套选择的前提是：这些子系统一旦降级，失败是静默的。egress 空跑不会报错，只会放行流量；Vault 不注入不会报错，只会让请求变成未认证。静默的安全降级比中断危险得多，所以选择中断。

代价：sidecar 的一个 bug 可以让整个沙箱不可用；Vault socket 成为数据面硬依赖。文档把这条写成运维要求（监控 sidecar 与私有 socket），而不是隐藏它。

六、单活控制面换实现简单

得到的：没有 leader election、没有分布式锁、状态机是单线程思维；快照的双副本协调只需三条不变量（先观察再创建、终态 CAS、恢复扫描）。

放弃的：控制面可用性。升级时短暂中断；服务器崩溃时无法创建/删除沙箱（运行中的沙箱不受影响）。

为什么可以接受：控制面的故障域与数据面解耦。沙箱里跑的命令不会因为控制面重启而中断。这是第 2 篇「两个平面」划分的直接收益。

什么时候失效：当控制面调用密集到升级窗口无法接受时（例如大规模 RL 训练每秒创建上百个沙箱）。ROADMAP 里「System-wide high availability」仍是 Planned，说明这个阈值还没被到达，或还没被解决。

七、静态文档换能力协商

兼容性文档承担了「能力清单」的职责。它有效的原因是它准确且有人维护；它脆的原因是没有机器可读的校验。

一个具体的风险：文档说「Kubernetes rootfs 快照提交器拒绝 gVisor RuntimeClass」。如果某天这个限制被解除，文档不改，用户就会继续避开一个已经不存在的坑——这是软性的损失。反过来如果新增限制没写，用户会撞上一个没人告知的失败。

替代方案是能力发现端点，或者把限制编码进错误码/错误消息。上游已经有一半：/v1/isolated/capabilities、OPEN-SANDBOX-ORIGIN 头、DIAGNOSTICS_* 错误码。这些是局部的能力发现，缺的是全局的。

八、SSE 换双向流

数据面用 SSE 而不是 WebSocket（PTY 除外）。

得到的：浏览器与普通 HTTP 客户端都能消费；代理友好；实现简单（一行 data: {...}\n\n）。

放弃的：双向控制通道。所以要中断命令只能另发一个 DELETE /command；所以「客户端断开」与「命令失败」必须用事件语义区分（第 9 篇那三条语义正是为此）。

付过的代价：exit_code 字段的加入让老 SDK 崩溃（kotlinx-serialization 的未知字段问题）。这是一个很好的教训：在强类型客户端生态里，给事件加字段不是向后兼容的操作，除非客户端屏蔽了自己的序列化运行时。

九、绝对 TTL 换空闲友好

得到的：寿命可审计，从创建时间就能算；重启不重置。

放弃的：符合直觉的「用着就不会过期」。为此需要另外两个机制补：renew-on-access 与空闲暂停。

这三个机制（绝对 TTL、访问续期、空闲暂停）合起来其实是一套更复杂的语义，比单纯的 idle timeout 复杂。这是「可审计」这个属性换来的复杂度——它换来的是「这个沙箱为什么还活着」永远有一个确定答案。

十、三种后端各有一套持久性语义

暂停保留 持久性保证
Docker 进程现场（冻结） commit 成本地镜像后才持久，且只在这台机器
Kubernetes rootfs（内存仅在 QEMU 模式） 快照 Succeed + 镜像已推送
Fast Sandbox rootfs + vmstate + 内存 检查点完整落 store 才算 Paused

这三行的差异是能力差异，不是实现细节。它们没法被契约统一，只能被文档说明。

教学推演：如果重来一次，我会考虑把「持久性等级」做成创建请求里的显式字段（例如 durability: none|rootfs|memory），让不支持该等级的后端直接拒绝请求。这样调用方能声明意图，而不是读文档猜。这是本书里我最想提的一个改动建议。

沙箱密度要求高 共享数据面基础设施，但要准备接受执行路径的复杂度
子系统的失败是静默的 fail closed，并监控那个「硬依赖」
控制面调用不密集 单活 + 明确的中断窗口声明，胜过多活带来的分布式复杂度
有多种持久性语义 让调用方显式声明等级，别让文档承担这个职责

一个整体判断

这套设计最值得学的地方不是任何一个机制，而是它把不确定写进了接口和文档：

  • 状态带 reason；
  • 诊断带 truncated；
  • 日志带 complete/incomplete；
  • 指标把「拒绝」与「坏了」分开；
  • 文档写「这里不保证」「这次测量不建立结论」「这个限制仍在」；
  • 紧凑的地方（并发 20、恢复 62 秒、node agent 默认值）主动标注为未验证。

一个系统愿意承认这些，说明它的作者知道平台类软件的真正风险不是「功能少」，而是「用户以为它有某个保证而其实没有」。第 19 篇会用一次请求把这份清单重新走一遍。

本章要点

  • 十个结构性权衡：前缀分发、单契约、预热、sidecar vs 共享、fail-closed、单活、静态文档、SSE、绝对 TTL、三种持久性语义。
  • 每个取舍都有「什么时候失效」的条件，而不是无条件正确。
  • fail-closed 的前提是「降级是静默的」；静默的安全降级比中断更危险。
  • 单活控制面可接受，因为控制面故障域与数据面解耦。
  • 静态兼容性文档是当前的能力清单，但没有机器可读校验；局部能力发现（/capabilities、OPEN-SANDBOX-ORIGIN）已经存在。
  • 最值得改的一处：把持久性等级变成创建请求里的显式字段。

完结篇：跟着一次请求走完全书

这一篇把全书串一遍。场景是第 1 篇那个修 bug 的编码 Agent：它要为一次任务申请一个沙箱，跑测试，装一个依赖，改代码，再跑一次，最后交 diff。

请求：POST /v1/sandboxes

客户端带着 OPEN-SANDBOX-API-KEY，body 里是一份意图：

{
  "image": { "uri": "python:3.12" },
  "entrypoint": ["sleep", "infinity"],
  "resourceLimits": { "cpu": "2", "memory": "2Gi" },
  "timeout": 1800,
  "networkPolicy": {
    "defaultAction": "deny",
    "egress": [
      {"action": "allow", "target": "pypi.org"},
      {"action": "allow", "target": "*.github.com"}
    ]
  },
  "credentialProxy": { "enabled": true },
  "lifecycle": { "idlePolicy": { "idleTimeoutSeconds": 600, "onIdle": "pause", "wakeOnAccess": true } },
  "metadata": { "task": "fix-issue-418" }
}

这份 JSON 里每个字段都对应前面某一篇的一个机制：

字段 由谁处理 在哪一篇
image 运行时后端创建容器/工作负载 6 / 7
entrypoint 容器入口或分配后的 task 6 / 7
resourceLimits 后端翻译成容器限额或 Pod 资源 6 / 7
timeout 绝对 TTL + 过期定时器/expireTime 13
networkPolicy egress sidecar 或共享 egress subject 11
credentialProxy 挂 egress 并启用 MITM 与 vault 12
idlePolicy 空闲扫描器 + 唤醒路径 13
metadata 标签/注解，可被列表过滤 4 / 6

第 1 毫秒：控制面

RequestIdMiddleware 生成或透传请求 ID。AuthMiddleware 校验 key：单租户比对 server.api_key，多租户交给 TenantProvider 并把租户命名空间写进 ContextVar（第 14 篇）。

路由进入 api.lifecycle.create_sandbox，四步校验：extensions 合法性、renewal 与 extensions 的冲突、networkPolicy 归一化、snapshotId 解析（这里没有 snapshot，跳过）。然后委派给 sandbox_service（第 4 篇）。

因为 runtime.type = "kubernetes"，实际对象是 CompositeSandboxService；因为没有 templateId，请求走到 KubernetesSandboxService（第 5 篇）。

第一个 100 毫秒：认领容量

服务器创建 BatchSandbox，带 expireTime、Pod 模板合并后的资源与平台约束、egress sidecar 的追加、以及网络策略的注解。

如果集群里有 Pool，控制器会把一个已经 Running+Ready 的预热 Pod 标注给这个 BatchSandbox，写 alloc-status 注解；entrypoint 作为分配后的 task 下发，而不是改写 Pod。如果池空了，控制器写 PoolAllocationPending（reason PoolCapacityExhausted），服务器在有界窗口内等待，超时返回可重试的 429（第 7 篇）。

这条路径之所以是毫秒级，是因为调度、拉镜像、启动都发生在请求之前。这就是第 1 篇那条「快在已经存在的容量上」的兑现。

就绪：从 Pending 到 Running

服务器等工作负载进入 Running/Allocated（默认 60 秒上限），然后返回创建响应。客户端拿到的是一个 Pending 或 Running 的沙箱对象，带 state/reason/message(第 4 篇)。它至此不再需要轮询创建接口，而是从这个沙箱对象读所有后续状态。

同时发生的还有两件事：

  • egress sidecar 已经把 DNS 与 nftables 规则装好，默认拒绝，只放行 pypi 与 github（第 11 篇）；
  • execd 在容器里启动，等待 per-allocation 绑定；绑定未完成前，除 /ping//ready 外全部返回 503（第 9 篇）。

接入：解析 endpoint

客户端要跑命令，于是 GET /sandboxes/{id}/endpoints/44772。

服务器返回一个地址 + 需要的头。在 Kubernetes + ingress 部署下，通常是网关地址加 OpenSandbox-Ingress-To: <id>-44772；开了 secureAccess 时还带 endpoint 凭据；Fast Sandbox 的返回则是一个签名的 f1. scope（第 8、10 篇）。

这一步的返回值是凭据，不是普通字符串。 客户端要原样保留，不能丢头、不能截断路径。

干活：一次命令执行

客户端 POST /command，body 指定 argv 或 shell 语法。execd 执行并回 SSE：

data: {"type":"init"}
data: {"type":"stdout","text":"running 42 tests...\n"}
data: {"type":"stderr","text":"FAILED test_retry\n"}
data: {"type":"execution_complete","exit_code":1}

客户端必须按第 9 篇那三条语义解析：拼接事件还原输出（行尾原样）、execution_complete 的 exit_code 才算结论、流在终止事件前结束就当作不确定。

对应地，如果客户端是老版本 SDK 且 classpath 里有不兼容的 kotlinx-serialization，它可能解不出这个字段而挂住——这就是 EXECD_SSE_LEGACY_COMPAT 存在的原因。

装依赖：出向策略与凭据

Agent 要 pip install。请求发往 pypi.org：

  1. DNS 被重定向到 sidecar 的 DNS 代理，域名命中 allow 规则，正常解析并记录地址（第 11 篇）；
  2. nftables 放行该地址，租约有时限；
  3. 如果要访问的是需要认证的内部制品库，请求被 mitmproxy 拦截，绑定匹配后注入认证头；沙箱里的 PIP_INDEX_URL 里只有占位符或假值（第 12 篇）。

如果 Agent 尝试访问 169.254.169.254 或者 metadata.internal：DNS 返回 NXDOMAIN，或者包被 nftables 丢弃。平台覆盖规则永远优先于租户规则——即使请求里写了 allow（第 11 篇）。

访问中途：续期与空闲暂停

这个任务跑了 40 分钟。期间客户端每隔一段时间唤醒沙箱访问一次：

  • 每次经网关的请求都会发布一次 renew-intent，沙箱的绝对过期时间被延长（第 13 篇）；
  • 如果客户端停了 10 分钟（超过 idleTimeoutSeconds: 600），空闲扫描器把它暂停：Kubernetes 后端会提交 rootfs 镜像、释放 Pod；
  • 下一次访问时，wakeOnAccess: true 让它自动唤醒，但地址变了，客户端必须重新解析 endpoint（第 13、10 篇）。

如果部署的是 Fast Sandbox，唤醒可能是检查点恢复，并且在另一台宿主机上——重新解析不是可选动作。

交付：快照还是 diff

任务结束有两种收尾：

交 diff：直接用文件 API 从工作区读改动，然后删除沙箱。删除是异步的：DELETE 返回 204，之后 GET 会看到 Stopping，清理完成变 404。

保留现场：POST /sandboxes/{id}/snapshots 创建快照。只有 Running 源可以创建；记录从 Pending → Creating → Publishing → Succeeded；只有 Succeeded 之后才是一个可复用的起点，从它创建出的是新沙箱 ID（第 13 篇）。

注意这里有一个不对称：快照成功之后，沙箱本身的后续写入不会被自动快照；进程退出、OOM、驱逐都不会自动保存。想要可复现环境，就得显式做快照——这条边界在第 13 篇被反复强调，因为它是「暂停能不能当备份用」的唯一答案。

收尾

回到开头那个问题：POST /v1/sandboxes 之后发生了什么。

答案是六件事同时发生：控制面校验并委派、运行时认领已有容量、数据面准备好执行接口、网络装上默认拒绝的策略、凭据被留在沙箱之外、生命周期开始倒计时。它们分别由四个进程、三个后端、四份契约保证，并且每一处不确定都被写成了可检查的字段。

这套系统的价值不在于它有多少功能，而在于它把「承诺」和「不承诺」分得很清。第 18 篇列的那些取舍，本质上都是同一件事的不同侧面：在能保证的地方给出强保证，在不能保证的地方留下可验证的痕迹。

读到这里，如果你要做一个类似的执行层，我希望你带走的是这句话，而不是任何具体实现：

沙箱平台的难点从来不是把容器跑起来，而是让「隔离」「快」「可解释」这三件事在同一个请求里同时成立，并且诚实地告诉使用者哪一件打了折。

本章要点

  • 一次请求会依次穿过：认证与租户 → 校验与委派 → 容量认领 → 就绪 → endpoint 解析 → 命令/文件/代码执行 → 出向策略与凭据 → 续期/空闲暂停 → 快照或删除。
  • 每个阶段都有一个「第一现场」：状态字段、条件、事件、指标或日志。
  • 三条改动路径：加后端（实现接口 + 前缀 + 文档）、改出向（优先级与 deny-first）、加执行能力（分层与绑定重置）。

#!/usr/bin/env python3
"""mini_osb —— 用标准库复刻 OpenSandbox 的骨架。

这里没有容器、没有 Kubernetes、没有 Firecracker。它只保留本书讨论的
结构性决定，每个决定都能对应到上游源码里的一个文件：

    Server(api + service 工厂)   -> server/opensandbox_server/services/factory.py
    SandboxService 接口          -> server/opensandbox_server/services/sandbox_service.py
    按 ID 前缀路由的 Composite   -> server/opensandbox_server/services/composite_service.py
    单主机端口 + /proxy/{port}   -> components/execd 的内置反向代理
    Pool 预热与分配注解          -> kubernetes/internal/controller/pool_controller.go
    execd 的 SSE 事件与退出码    -> components/execd/pkg/web/model/codeinterpreting.go
    egress 的规则优先级          -> components/egress/pkg/policy/always_rules.go
    绝对过期时间与暂停/恢复             -> docs/guides/pause-resume.md

运行：python3 examples/mini_osb.py
测试：python3 -m unittest discover -s examples -v
"""

from __future__ import annotations

import json
import time
from dataclasses import dataclass, field
from enum import Enum
from typing import Callable, Iterable


class State(str, Enum):
    PENDING = "Pending"
    RUNNING = "Running"
    PAUSING = "Pausing"
    PAUSED = "Paused"
    RESUMING = "Resuming"
    STOPPING = "Stopping"
    TERMINATED = "Terminated"
    FAILED = "Failed"


class SandboxError(Exception):
    """服务层对外只抛一种错误，附带 HTTP 语义的状态码。"""

    def __init__(self, status: int, code: str, message: str) -> None:
        super().__init__(f"{status} {code}: {message}")
        self.status, self.code, self.message = status, code, message


@dataclass
class Sandbox:
    id: str
    image: str
    state: State
    expires_at: float | None
    entrypoint: list[str]
    env: dict[str, str] = field(default_factory=dict)
    metadata: dict[str, str] = field(default_factory=dict)
    node: str | None = None
    # 数据面地址：单主机后端只有一个 host proxy 端口，K8s 后端是 pod IP。
    data_plane: tuple[str, int] | None = None
    # 只有 paused 时才有值：恢复时要读回的 rootfs 快照 ID。
    snapshot: str | None = None
    reason: str | None = None
    message: str | None = None


# --------------------------------------------------------------------------
# 数据面：一个 execd 替身。命令执行走“事件流 + 终止事件”，不是返回值。
# --------------------------------------------------------------------------

@dataclass
class Event:
    """对应 execd 的 ServerStreamEvent：type/text/exit_code。"""

    type: str
    text: str = ""
    exit_code: int | None = None

    def to_sse(self) -> str:
        payload = {"type": self.type}
        if self.text:
            payload["text"] = self.text
        if self.exit_code is not None:
            payload["exit_code"] = self.exit_code
        return f"data: {json.dumps(payload, ensure_ascii=False)}\n\n"


class Execd:
    """沙箱内守护进程：命令、文件、指标。全部在进程内模拟。"""

    def __init__(self) -> None:
        self.files: dict[str, bytes] = {}
        self.env: dict[str, str] = {}

    def run(self, argv: list[str]) -> list[Event]:
        if not argv:
            return [Event("error", "argv must not be empty"), Event("execution_complete", exit_code=2)]
        out = " ".join(argv)
        # 只认识一个内置命令；其他命令都当作成功的 echo，避免真的执行外部程序。
        if argv[0] == "false":
            return [Event("stderr", "command failed\n"), Event("execution_complete", exit_code=1)]
        if argv[0] == "ls":
            body = "\n".join(sorted(self.files)) or ""
            return [Event("stdout", body + ("\n" if body else "")), Event("execution_complete", exit_code=0)]
        return [Event("stdout", f"{out}\n"), Event("execution_complete", exit_code=0)]

    def write_file(self, path: str, data: bytes) -> None:
        # 上游把上传写到目标旁边的暂存文件再 rename；这里只保留“不会写一半”的语义。
        staged = f"{path}.stage"
        self.files[staged] = data
        self.files[path] = self.files.pop(staged)

    def read_file(self, path: str) -> bytes:
        if path not in self.files:
            raise SandboxError(404, "FILE_NOT_FOUND", path)
        return self.files[path]


# --------------------------------------------------------------------------
# 出向网络：两条层（DNS 与网络）在本书里压成一次求值，但优先级保持原样。
# --------------------------------------------------------------------------

@dataclass(frozen=True)
class Rule:
    action: str  # "allow" | "deny"
    target: str  # "pypi.org" / "*.pypi.org" / "10.0.0.0/8"

    def matches(self, host: str) -> bool:
        if self.target.startswith("*."):
            return host.endswith(self.target[1:])
        return host == self.target


class Egress:
    """platform deny.always > platform allow.always > 用户策略。"""

    def __init__(self, deny_always: Iterable[Rule] = (), allow_always: Iterable[Rule] = ()) -> None:
        self.deny_always = list(deny_always)
        self.allow_always = list(allow_always)
        self.rules: list[Rule] = []
        self.default_action = "deny"

    def add(self, *rules: Rule) -> None:
        self.rules.extend(rules)

    def decide(self, host: str) -> str:
        for rule in self.deny_always:
            if rule.matches(host):
                return "deny"
        for rule in self.allow_always:
            if rule.matches(host):
                return "allow"
        for rule in self.rules:  # 用户策略：第一条命中的规则生效
            if rule.matches(host):
                return rule.action
        return self.default_action


# --------------------------------------------------------------------------
# 控制面：一个接口，两个后端。
# --------------------------------------------------------------------------

class SandboxService:
    """所有运行时实现同一套生命周期语义；API 层不认识容器或 Pod。"""

    id_prefix = ""

    def __init__(self) -> None:
        self.sandboxes: dict[str, Sandbox] = {}

    def ready(self, sandbox: Sandbox) -> None:
        sandbox.state = State.RUNNING
        sandbox.reason = "Ready"
        sandbox.message = "sandbox is running"

    def create(self, request: "CreateRequest") -> Sandbox:
        raise NotImplementedError

    def get(self, sandbox_id: str) -> Sandbox:
        sandbox = self.sandboxes.get(sandbox_id)
        if sandbox is None:
            raise SandboxError(404, "SANDBOX_NOT_FOUND", sandbox_id)
        return sandbox

    def list(self) -> list[Sandbox]:
        return sorted(self.sandboxes.values(), key=lambda s: s.id)

    def delete(self, sandbox_id: str) -> None:
        sandbox = self.get(sandbox_id)
        sandbox.state = State.STOPPING
        self.sandboxes.pop(sandbox_id)

    def pause(self, sandbox_id: str) -> None:
        sandbox = self.get(sandbox_id)
        if sandbox.state == State.PAUSED:
            raise SandboxError(409, "SANDBOX_ALREADY_PAUSED", sandbox_id)
        if sandbox.state != State.RUNNING:
            raise SandboxError(409, "SANDBOX_NOT_RUNNING", f"{sandbox_id} is {sandbox.state.value}")
        sandbox.state = State.PAUSING
        sandbox.snapshot = f"snap-{sandbox_id}"  # 先写快照，再报 Paused
        sandbox.state = State.PAUSED
        sandbox.node = None
        sandbox.data_plane = None

    def resume(self, sandbox_id: str) -> Sandbox:
        sandbox = self.get(sandbox_id)
        if sandbox.state != State.PAUSED:
            # resume 是暂停态操作，不是通用重启；已退出就是 Terminated/Failed。
            raise SandboxError(409, "SANDBOX_NOT_PAUSED", f"{sandbox_id} is {sandbox.state.value}")
        if sandbox.snapshot is None:
            raise SandboxError(409, "SANDBOX_SNAPSHOT_MISSING", sandbox_id)
        sandbox.state = State.RESUMING
        self._restore(sandbox)
        self.ready(sandbox)
        return sandbox

    def _restore(self, sandbox: Sandbox) -> None:
        raise NotImplementedError

    def endpoint(self, sandbox_id: str, port: int) -> dict[str, str]:
        raise NotImplementedError


class SingleHostRuntime(SandboxService):
    """Docker 形态：每个沙箱只映射一个 host 端口，其余端口走 /proxy/{port}。"""

    id_prefix = "sbx-"
    PROXY_PORT = 44772

    def __init__(self) -> None:
        super().__init__()
        self._next_host_port = 40000

    def create(self, request: "CreateRequest") -> Sandbox:
        sandbox = Sandbox(
            id=f"sbx-{len(self.sandboxes) + 1:04d}",
            image=request.image,
            state=State.PENDING,
            expires_at=request.expires_at(),
            entrypoint=list(request.entrypoint),
            env=dict(request.env),
            metadata=dict(request.metadata),
        )
        self.sandboxes[sandbox.id] = sandbox
        self._next_host_port += 1
        sandbox.data_plane = ("127.0.0.1", self._next_host_port)
        sandbox.node = "localhost"
        self.ready(sandbox)
        return sandbox

    def _restore(self, sandbox: Sandbox) -> None:
        # 容器级 pause/resume 保留容器，所以恢复只是取消冻结；host 端口不变。
        self._next_host_port += 1
        sandbox.data_plane = ("127.0.0.1", self._next_host_port)
        sandbox.node = "localhost"

    def endpoint(self, sandbox_id: str, port: int) -> dict[str, str]:
        sandbox = self.get(sandbox_id)
        if sandbox.state != State.RUNNING or sandbox.data_plane is None:
            raise SandboxError(503, "SANDBOX_NOT_READY", sandbox_id)
        host, proxy_port = sandbox.data_plane
        if port == self.PROXY_PORT:
            return {"url": f"http://{host}:{proxy_port}"}
        # 所有容器端口共用一个 host 端口，路径前缀是唯一的路由信息。
        return {"url": f"http://{host}:{proxy_port}/proxy/{port}", "headers": {}}


class PoolRuntime(SandboxService):
    """Kubernetes + Pool 形态：预热 Pod 是容量，分配是标注，不是调度。"""

    id_prefix = "sbx-"
    CAPACITY = 2

    def __init__(self) -> None:
        super().__init__()
        self.warm: list[str] = [f"pod-{i}" for i in range(1, self.CAPACITY + 1)]
        self.allocated: dict[str, str] = {}  # sandbox_id -> pod

    def create(self, request: "CreateRequest") -> Sandbox:
        if not self.warm:
            raise SandboxError(429, "POOL_CAPACITY_EXHAUSTED", "no warm pod available")
        pod = self.warm.pop(0)
        sandbox = Sandbox(
            id=f"sbx-{len(self.sandboxes) + 1:04d}",
            image=request.image,
            state=State.PENDING,
            expires_at=request.expires_at(),
            entrypoint=list(request.entrypoint),
            env=dict(request.env),
            metadata=dict(request.metadata),
            node=pod,
        )
        self.sandboxes[sandbox.id] = sandbox
        self.allocated[sandbox.id] = pod
        # 预热 Pod 没有镜像信息，entrypoint 只能作为分配后的 task 下发。
        sandbox.metadata.setdefault("opensandbox.io/task", json.dumps(sandbox.entrypoint))
        sandbox.data_plane = (f"10.0.0.{len(self.allocated)}", 44772)
        self.ready(sandbox)
        return sandbox

    def _restore(self, sandbox: Sandbox) -> None:
        # 恢复不保证落回原 Pod：IP 会变，客户端必须重新解析 endpoint。
        sandbox.node = self.allocated.get(sandbox.id, "pod-recycled")
        sandbox.data_plane = (f"10.0.0.{len(self.allocated) + 10}", 44772)

    def endpoint(self, sandbox_id: str, port: int) -> dict[str, str]:
        sandbox = self.get(sandbox_id)
        if sandbox.state != State.RUNNING or sandbox.data_plane is None:
            raise SandboxError(503, "SANDBOX_NOT_READY", sandbox_id)
        host, _ = sandbox.data_plane
        return {"url": f"http://{host}:{port}", "headers": {"OpenSandbox-Ingress-To": f"{sandbox_id}-{port}"}}

    def delete(self, sandbox_id: str) -> None:
        super().delete(sandbox_id)
        pod = self.allocated.pop(sandbox_id, None)
        if pod is not None:
            self.warm.append(pod)  # recycleStrategy=Delete：换一个干净的 Pod


@dataclass
class CreateRequest:
    image: str
    timeout: float | None = 600.0
    entrypoint: list[str] = field(default_factory=list)
    env: dict[str, str] = field(default_factory=dict)
    metadata: dict[str, str] = field(default_factory=dict)
    now: float = field(default_factory=time.time)

    def expires_at(self) -> float | None:
        # 绝对 TTL：之后无论是重启还是暂停都不会重置。
        return None if self.timeout is None else self.now + self.timeout


class CompositeService(SandboxService):
    """一个 runtime.type，两种创建路径：镜像走 Pod，模板走 fsb。"""

    def __init__(self, pod_backend: PoolRuntime, template_backend: SandboxService | None = None) -> None:
        super().__init__()
        self.pod_backend = pod_backend
        self.template_backend = template_backend

    def _route(self, request: CreateRequest) -> SandboxService:
        if request.metadata.get("templateId") and self.template_backend is not None:
            return self.template_backend
        return self.pod_backend

    def create(self, request: CreateRequest) -> Sandbox:
        return self._route(request).create(request)

    def _backend(self, sandbox_id: str) -> SandboxService:
        # 上游用 "fsb-" 前缀分发既有沙箱；这里用同一个思路。
        if sandbox_id.startswith("fsb-") and self.template_backend is not None:
            return self.template_backend
        return self.pod_backend

    def get(self, sandbox_id: str) -> Sandbox:
        return self._backend(sandbox_id).get(sandbox_id)

    def list(self) -> list[Sandbox]:
        return self.pod_backend.list() + (self.template_backend.list() if self.template_backend else [])

    def delete(self, sandbox_id: str) -> None:
        self._backend(sandbox_id).delete(sandbox_id)

    def pause(self, sandbox_id: str) -> None:
        self._backend(sandbox_id).pause(sandbox_id)

    def resume(self, sandbox_id: str) -> Sandbox:
        return self._backend(sandbox_id).resume(sandbox_id)

    def endpoint(self, sandbox_id: str, port: int) -> dict[str, str]:
        return self._backend(sandbox_id).endpoint(sandbox_id, port)


def create_service(runtime: str) -> SandboxService:
    """对应 services/factory.py：配置决定实现，API 层不写 if runtime == ..."""
    if runtime == "docker":
        return SingleHostRuntime()
    if runtime == "kubernetes":
        return CompositeService(PoolRuntime(), TemplateRuntime())
    raise ValueError(f"Unsupported runtime: {runtime}")


class TemplateRuntime(SandboxService):
    """fsb 形态：模板决定工作负载，创建请求只表达意图（谁、多久）。"""

    id_prefix = "fsb-"
    counter = 0

    def create(self, request: CreateRequest) -> Sandbox:
        if request.entrypoint or request.env:
            raise SandboxError(400, "TEMPLATE_FIELD_REJECTED", "entrypoint/env come from the template")
        TemplateRuntime.counter += 1
        sandbox = Sandbox(
            id=f"fsb-{TemplateRuntime.counter:04d}",
            image=f"template:{request.metadata['templateId']}",
            state=State.PENDING,
            expires_at=request.expires_at(),
            entrypoint=[],
            metadata=dict(request.metadata),
            node="fastlet-1",
            data_plane=("10.30.0.5", 44772),
        )
        self.sandboxes[sandbox.id] = sandbox
        self.ready(sandbox)
        return sandbox

class Server:
    def __init__(self, runtime: str, api_key: str | None = None, now: float | None = None) -> None:
        if api_key is None and runtime != "docker":
            # 上游在非交互环境里拒绝无 API key 启动（startup_guard.api_key_confirm）。
            raise SystemExit("refusing to start without an API key outside local development")
        self.service = create_service(runtime)
        self.api_key = api_key
        self.clock = now if now is not None else time.time

    def _auth(self, key: str | None) -> None:
        if self.api_key is not None and key != self.api_key:
            raise SandboxError(401, "UNAUTHORIZED", "missing or invalid OPEN-SANDBOX-API-KEY")

    def create(self, key: str | None, request: CreateRequest) -> Sandbox:
        self._auth(key)
        request.now = self.clock()
        return self.service.create(request)

    def get(self, key: str | None, sandbox_id: str) -> Sandbox:
        self._auth(key)
        sandbox = self.service.get(sandbox_id)
        if sandbox.expires_at is not None and self.clock() >= sandbox.expires_at:
            sandbox.state = State.TERMINATED
            sandbox.reason = "Expired"
        return sandbox

    def endpoint(self, key: str | None, sandbox_id: str, port: int) -> dict[str, str]:
        self._auth(key)
        return self.service.endpoint(sandbox_id, port)

    def expire(self) -> list[str]:
        """过期是绝对的：扫描只看 expires_at，不看最后一次访问时间。"""
        expired = [
            sandbox.id
            for sandbox in self.service.list()
            if sandbox.expires_at is not None and self.clock() >= sandbox.expires_at
        ]
        for sandbox_id in expired:
            self.service.delete(sandbox_id)
        return expired
